# Architecture

The repository's parts, how data moves between them, and the layers the web app keeps. Terms are as [CONTEXT.md](CONTEXT.md) defines them.

## The parts

| Part | What it is |
| --- | --- |
| `apps/web/` | Farty: a Next.js app on Cloudflare Workers, installable from the browser. Each environment has its own Worker, D1 database and R2 bucket ([the web app guide](docs/agents/web.md)). |
| `tools/melody-lab/` | The reference engine, in Python: Recording Analysis, Auto-map and the fart-only renderer, as approved by ear. |
| `fixtures/golden/` | The reference engine's answers for the Fixture Library and the Song Catalog. They are the contract between the reference and the web app. |
| `fixtures/recordings/` | The Fixture Library: real Recordings, with their licenses, for tests and tools. It never ships to Production. |
| `catalog/` | The Song Catalog's cited public-domain scores, imported by `tools/catalog/`. |

## How the web app stays matched to the reference

`tools/melody-lab/export_golden.py` writes the reference's answers to `fixtures/golden/`. The web app's unit tests run its own Recording Analysis and engine on the same Recordings and Songs and compare: Recording Pitch must be bit-identical, which is why `src/lib/analysis/numeric.ts` rounds `exp2` and `log2` as numpy does. `src/lib/catalog/generate.ts` writes the Songs the app ships from the golden copy of each score, so no melody is typed by hand. A change to the reference changes the golden data in the same commit, and the web app follows it. What the port must reproduce, and why, is in [Matching the reference](docs/agents/matching-the-reference.md).

The renders are checked the other way round: `apps/web/scripts/render-songs.ts [out-dir]` renders every Song through the web engine with the full Fixture Library, into the melody lab's git-ignored output folder by default. For each Song it writes the renderer's exact output as a 32-bit float WAV and its notes as JSON, each note's event with `lead_s`, the quiet lead-in played before the beat (#287), for `tools/melody-lab/evaluate_renders.py` to measure. It fails when a Song that the golden Arrangement unlocks comes out locked. With `--scenario ../../tools/melody-lab/scenarios/<id>.json [out-dir]` it renders a Scenario's library instead, into `tools/melody-lab/out/web-<id>/` by default: the fixtures it lists, each trimmed between its handles (`trimBounds`, ADR 0019) and placed on its note by ear (ADR 0015) as the app does it, arranged from the Melodic and placed Recordings as `autoMapRecordings` reads them. `evaluate_renders.py --scenario` checks those, with nothing compared to golden.

## How data moves in the web app

1. **Recording:** the microphone feeds an AudioWorklet (`src/lib/audio/`) with the browser's voice processing off, so a take is the microphone's raw level. Record's level is measured batch by batch as the take comes in (`TakeLevels`): its bars, one per 50 ms from 0 at −70 dBFS to 1 at full scale, are the live waveform (#314), and about 2 s in the take so far is judged as Stop will judge it, so "Can't hear anything" during the take and "Didn't catch that" at Stop never disagree (#281). A take is kept only when it heard something: its loudest 50 ms reaches −70 dBFS and stands 4 dB above the take's own room (`heardSomething`), a gate the reference doesn't have. Every Fixture Library fart whose loudest sample reaches −50 dBFS passes (#279); below −70 is near-silence that turning it up would only make loud hiss, and a low rumble down to −70 is a known false accept, in which analysis finds no steady note. A heard take is saved turned up by one gain so its loudest sample reaches 0.89, about −1 dBFS as a rendered Song peaks, in float before the 16-bit save, and never turned down (`atFullLevel`, #279); Recording Analysis gives the same answers either way.
2. **The review and the save:** the take on review (`draft-session.ts`) is encoded once as the WAV it saves as, and its analysis starts at Stop on that WAV, so it finds what a saved Recording's would. Save writes the Recording to IndexedDB at once, with the note and name the review changed (ADR 0002); its Trim, found in the analysis worker, and its analysis follow.
3. **Recording Analysis** runs in a Web Worker (`src/lib/analysis/`) and is kept with the Recording. A new analysis, a Re-scan's and the upgrade's among them, changes only the analysis, so a Placed Pitch, Trim or name saved while it ran stays ([ADR 0017](docs/adr/0017-a-second-pitch-window-and-re-scan.md), ADR 0019).
4. **The Song Catalog** ships as data, not code (#322): `src/lib/catalog/load-songs.ts` fetches the index once (`catalog-path.generated.ts` names it by its content), and a Song's notes only when it opens, so Compose stays quick with 1,000 Songs and the build reads only its own catalog. Every app page's head names the index (`preload`); a shared page (`/u/`) neither names nor fetches it.
5. **Compose, Song Creator and the Sound Pad:** Pitch Coverage decides which Songs are unlocked. Auto-map chooses the Arrangement, and the renderer plays it with the Recordings, in its own Web Worker (`src/lib/engine/`). The Sound Pad plays each Recording raw from where a Song starts it, and its take, a Performance, renders in the same worker ([ADR 0017](docs/adr/0017-sound-pad-takes-save-as-toots.md)). A saved result is a Toot.
6. **An account** (free, and needed to keep farts past the visit, ADR 0013) syncs the library: each save, rename, placement by ear, Trim, name, Favorite Song and delete waits in an outbox with the change itself, and the sync sends it to the API (`src/app/api/`, `src/server/`), which keeps Recordings, Toots and Favorite Songs in D1 and their audio in R2. Saving a Toot needs one, and is paid through Stripe Checkout ([Payments](docs/agents/payments.md)).
7. **Sharing:** a signed-in user shares a saved Recording or Toot by an unlisted link under their Handle, and adds friends by Handle. The public pages under `/u/` read D1 on every request, so a stopped or taken-down link is gone at once ([Sharing, friends and reports](docs/agents/sharing.md)).

## Offline: the service worker

`public/sw.js` keeps the app shell so an installed Farty opens offline.

- **Network first.** Every same-origin GET it handles goes to the network, so a deploy shows at once. The kept copy answers only offline, or when a deploy has removed a file that a tab opened before the deploy still loads: an older build's `/_next/static/` file (#222), or the Song Catalog's index or a Song's notes, which are named by their content too. A build's files never change under the same name.
- **What it keeps:** pages, scripts, styles, fonts and images, only from a whole same-origin 200 (never a redirect, an error or Staging's 401), up to 200 files, oldest first. It never keeps audio (Recordings live in IndexedDB), the Fixture Library (`/fixtures/`, internal only), or the lander's images (`/lander/`, desktop only, #191), and it never handles a shared link (`/u/`), so no copy of a stopped link's page opens.
- **One Song page.** It keeps `/compose/song/` and answers every Song's page with it offline, which reads the Song from the address (#322). It never keeps a Song's own page, even one loaded online: nothing would refresh it, so after a deploy it would load an older build's code and catalog beside the current build's database.
- **Song notes** are kept in a cache of their own, up to 2000 files, so they never push the shell out. Once it has an index (on install, and whenever a page fetches one), it fetches every Song's notes it hasn't kept, six at a time and in the background, so a Song never opened plays offline too (#138). It remembers each index it has done, since an index's notes never change, and tries one again only when a fetch failed. A notes 404 is notes a deploy took off the server; the next index names their successor.
- **The whole shell, ahead of time:** each online load of the start page (`/`), at most every five minutes, fetches the tabs it links to, the pages `/shell.json` lists (the one Song page, the Sound Pad and the one Toot page), and the scripts they load, including the Web Workers' own chunks. Every tab then opens offline right after install, even one never visited. A load that loses the connection part way tries again on the next start page.
- **Staging's password:** a navigation answered with Staging's 401 unregisters the worker, since a browser won't ask for credentials on a worker's behalf. The next load asks for the password and registers it again.
- **Versions:** the caches are `pedos-shell-v<version>` and `pedos-notes-v<notesVersion>`. Raise `version` when the shell cache's contents change shape, and `notesVersion` when the notes cache's do; a new worker deletes every other version's caches when it activates.

## The web app's layout

- `src/lib/analysis/`: Recording Analysis, matched to the reference through `fixtures/golden/`. Plain TypeScript with no DOM or Web Audio, so it runs in the Web Worker (`worker.ts`) and in Vitest alike. `trimming.ts` finds the fart and a Trim's.
- `src/lib/engine/`: Auto-map and the fart-only renderer, matched to the reference: a Song (`render-song.ts`), a Recording's part with its lead-in (`render-source.ts`) and a Sound Pad Performance (`render-performance.ts`). Plain TypeScript, so it renders in its Web Worker (`worker.ts`) and in Vitest alike. `pnpm exec tsx scripts/render-songs.ts` renders every Song for `tools/melody-lab/evaluate_renders.py`.
- `src/lib/audio/`: the microphone and playback. `recorder.ts` runs a take, `microphone.ts` opens, moves and lets go of the microphone (an AudioWorklet, with the browser's voice processing off), `keep-microphone-open.ts` keeps it open for the launch once Record shows, `microphone-grant.ts` tracks whether it may open without a tap, `player.ts` plays a sound and reads its playhead, and `pad-player.ts` plays the Pads.
- `src/lib/catalog/`: the Song Catalog as data (#322, #323). `generate.ts` writes the index and each Song's notes into `public/catalog/`, named by their content, and the modules that name them; `load-songs.ts` fetches them; `search-key.ts` is Compose's search. Only routes and the server import `song-index.generated.ts`, and only tests `test-support/songs.generated.ts`, which it writes beside them. In the screens, `song-catalog-provider.tsx` fetches the index once for the app, `use-song-notes.ts` loads a Song's notes for Song Creator and a Toot's screen, and `songs-failed.tsx` says when the catalog didn't load, with Try again.
- `src/lib/recording-store.ts`: the `pedos` IndexedDB database, with Recordings (`recording-store.ts`), Toots (`toot-store.ts`), the Sound Pad's Pads (`pad-store.ts`, this browser's only) and Favorite Songs (`favorite-store.ts`), this browser's working copy. A guest's farts last only the visit (ADR 0013, #237; on 2026-10-28 this replaced #203's rule that a guest keeps their Recordings): each open reads the session, and a guest's new visit clears the last one's Recordings, Toots and Pads, except the Recordings the browser held before #237 (`visit.ts`). A guest's Favorite Songs outlast the visit and go to the account they sign in with.
- `src/lib/library-sync.ts`, `outbox.ts`, `outbox-send.ts`, `library-pull.ts`, `library-changes.ts`, `library-api.ts`: a signed-in browser's sync with the account (#156). Each save, rename, placement, Trim, name, Favorite Song and delete queues in the outbox with the change itself, one entry an item: a delete wins and drops an upload no request has carried, a rename or placement joins a waiting upload, and a Recording waits for its analysis. A `place` records which fields it changed (`fields`), so the PATCH leaves another browser's change to the others (ADR 0019); one without `fields` is from before #293 and means the Placed Pitch alone. A Favorite Song's last op wins, and a tap that undoes one no request carried leaves nothing to send. An op the code doesn't know, from a later build, stays queued and is never sent. The sync reads the account's changes since its last read (`library-pull.ts`), then uploads the outbox (`outbox-send.ts`). A Toot renamed or a Recording placed while its upload was on its way, or one the account already had, is renamed or placed on the account after it; a placement the account refuses is dropped, and a Favorite Song refused at the limit or for an unknown Song id is never retried. A Recording this browser already has takes only its Placed Pitch, Trim and name from a read, keeping this browser's own analysis, and a screen's list follows it (`recordingsAfter`). What this browser still has to send wins over what it reads; a full read, once the account's 30 days of tombstones have passed, deletes what it doesn't list; and Recordings not uploaded yet are numbered after the account's. Until the first read (`libraryPulled`), a Recording the account has may not be here yet, as right after signing in again. An upload the account refuses as full (409 `limit_reached`, `LIMITS` in `src/server/library.ts`) is marked `accountFull` on its outbox entry, which also drops its `sent`, so deleting it sends nothing; from then this page holds back every upload of that kind, marking each, until there may be room: a delete of that kind the account accepts (204), which lets the same sync try again, a read that deletes one of that kind here, or `claimLibrary` (each open signed in, and each new session). Then it sends the oldest, and holds again if that's refused. The hold lives in memory (`outbox-send.ts`), so it starts empty on each open. Recordings and Toots count the marked entries (`waitingForRoom`, read again on each outbox change), and Sign out tells them apart from farts merely not sent. `pedos.account` names the account the library is, and every library request names it (`x-pedos-library`), so a library never reads from, uploads to or deletes in another.
- `src/lib/account.ts`, `src/components/farty/account-provider.tsx`, `account-step.tsx`: the account from the browser (the sign-in API and `/api/account/`), and the account step after the first Result (#155), with Turnstile on sending a code (`turnstile.tsx`, #237). Every open reads the session, which renews its cookie once a day.
- `src/lib/recordings.ts`, `take-review.ts`, `src/components/farty/take-capture.ts`, `draft-session.ts`, `record-flow-provider.tsx`, `record-flow.tsx`, `record-cover.tsx`, `record-result.tsx`, `take-review.tsx`, `piano-keys.tsx`, `recording-review.tsx`: Record and its flow. `take-capture.ts` is the take being recorded, its states and live level (#281, #314); `draft-session.ts` the take on review, with its WAV, analysis and one decode; `take-review.tsx` the one review for every take (#314), with the review's piano keys, the one sound that isn't a fart (ADR 0015); `recording-review.tsx` a saved Recording's review, from its pencil.
- `src/components/farty/recordings-provider.tsx`, `use-rescan.ts`, `recording-replay.tsx`, `waveform.tsx`: the Recordings, their analysis and the Recordings tab. `use-rescan.ts` runs Re-scan one Recording at a time and keeps its last result until the next starts (#282, #295); `recording-replay.tsx` plays a row from a tap or a scrub, keeping only the waveform's bars, never the decoded take, which a library of a few hundred Recordings couldn't keep in a phone's memory (#299).
- `src/lib/pads.ts`, `pad-store.ts`, `audio/pad-player.ts`, `src/components/farty/sound-pad.tsx`, `pad.tsx`, `pad-chooser.tsx`: the Sound Pad (#277). Which Recording each Pad plays, and a player that decodes each Pad's sound ahead, cuts it in the render worker from where a Song starts the fart (#298), and starts a buffer of its own per tap.
- `src/lib/performance.ts`, `pad-take.ts`, `engine/render-performance.ts`, `src/components/farty/use-pad-take.ts`, `pad-take.tsx`, `pad-toot-layout.tsx`: the Sound Pad's Record (#278, [ADR 0017](docs/adr/0017-sound-pad-takes-save-as-toots.md)). A take's taps as a compact Performance, kept in `localStorage` by Toot id across Checkout (`pedos.padTakes`, only Recording ids and times, never audio, and only this library's), rendered in the render worker and saved as a Toot. A fixed number of takes of each kind, started a Checkout or not, are kept, so a new take never pushes out one that may be paid for.
- `src/lib/toot.ts`, `toot-renderer.ts`, `src/components/farty/save-to-toots.tsx`, `toot-layout.tsx`: a Toot, made in the render worker: a Song rendered with the user's Recordings, as Song Creator makes it, or a Sound Pad Performance (`makePadToot`, [ADR 0017](docs/adr/0017-sound-pad-takes-save-as-toots.md)), and Save to Toots for both.
- `src/lib/favorite-store.ts`, `src/components/farty/favorite-button.tsx`, `compose-choices.ts`: Favorite Songs (#313), a heart on each Song in Compose, its locked-Song sheet and Song Creator, synced with the account by Song id (`/api/favorites/{songId}/`). `compose-choices.ts` keeps Compose's sort and Favorites filter in `localStorage`.
- `src/lib/pricing.ts`, `toot-payment.ts`, `src/server/stripe.ts`, `toot-payments.ts`, `src/db/payments.ts`: paying $0.99 to save a Toot (ADR 0010, #204), through Stripe Checkout, or the dev checkout (`/dev/checkout/`) on a local run ([Payments](docs/agents/payments.md)).
- `src/lib/sharing.ts`, `handle.ts`, `src/server/sharing.ts`, `shared-audio.ts`, `reports.ts`, `public-route.ts`, `link-preview.tsx`, `wav-header.ts`, `src/db/sharing.ts`, `src/app/u/`, `src/components/farty/share-recording.tsx`, `handle-dialog.tsx`, `shared-recording-page.tsx`: sharing by unlisted link (#316, #317, ADR 0020). The owner's Handle and shares under `api/handle/` and `api/share/` (`userRoute`), and the public page, link image, audio and Report under `u/[handle]/r/[id]/` (a Recording) and `u/[handle]/t/[id]/` (a saved Toot), outside `api/` ([Sharing, friends and reports](docs/agents/sharing.md)).
- `src/lib/friends.ts`, `src/server/friends.ts`, `profiles.ts`, `src/db/friends.ts`, `profiles.ts`, `src/components/farty/friends.tsx`, `friends-section.tsx`, `add-friend-dialog.tsx`, `profile-page.tsx`: Friends and profile pages (#319, #346, ADR 0021). Requests, the lists and each friendship under `api/friends/` (`userRoute`), Friends in Profile, and the public profile page and its Report under `u/[handle]/`, which lists only live shares.
- `src/lib/get-farty.ts`, `src/components/farty/get-farty.tsx`, `src/app/u/layout.tsx`: Get Farty on a shared or profile page (#318). On a phone, the account step offers whoever's page it is as a friend, ticked, and sends the request only once they sign in there; then the Home Screen steps, which come after because the Home Screen app keeps its own storage. Its stage is kept in `sessionStorage` (`pedos.getFarty`), so a reload from Mail carries on, and it ends on any other page. On a computer, the lander's QR code, drawn on the server.
- `src/lib/security-headers.ts`: the headers every response carries, which `next.config.ts` sends with pages and `public/_headers` with the static files Production serves without the Worker.
- `src/db/`: the D1 schema (Better Auth's tables, `recordings`, `toots`, `toot_payments`, `favorite_songs`, sharing's `handles`, `shares` and `share_reports`, and friends' `friend_requests`, `friends` and `profile_reports`), `createDatabase()` over any D1 binding (`database.ts`, importable from tests) and `getDb()` for a request (`index.ts`, server-only), through Drizzle. Migrations are in `drizzle/`. Better Auth's tables are named after its models and write their own `created_at` and `updated_at`. Times are epoch milliseconds. A Recording's Placed Pitch (`placed_pitch`, ADR 0015; −1 is No note), Trim (the handles and the fart between them, ADR 0019) and `name` (#314) are columns apart from its `analysis`, which keeps the upload's: each changes alone (`PATCH /api/recordings/{id}/`, the last to arrive wins) and outlives each browser's own analysis. The account takes any MIDI note from 0 to 127, wider than the review's keys, so a later release can widen them; an upload from before #268 has none. A Toot is of a Song, with its Arrangement, or from the Sound Pad, with its Performance and no Song ([ADR 0017](docs/adr/0017-sound-pad-takes-save-as-toots.md)), which the `toots_song_or_performance` check holds; its SQL names its columns unqualified, since migration 0005 rebuilds `toots` through `__new_toots`, and its text must stay exactly as written or drizzle-kit sees a change. A deleted Recording, Toot or Favorite Song stays 30 days as a tombstone (`deleted_at`), so other browsers delete their copy, and an upload of its id answers 410; a browser whose last read is older gets the whole library (`full`). The one exception is a Fixture Library Recording everywhere but Production (`server/fixture-recordings.ts`): uploading its fixed id again drops the tombstone and keeps it again, so a tester can load a deleted fixture again. Every `updated_at` and `deleted_at` comes from D1's own clock (`d1-clock.ts`), and D1 runs one statement at a time, so a row changed after a library read is never older than that read's `cursor`. A Favorite Song is marked, and the result read, in one D1 batch, so neither two at once nor a delete between them gets a wrong answer.
- `src/app/api/`, `src/server/`: a signed-in user's library (Recordings, Toots, Favorite Songs and the WAVs in R2) and account. Every route outside `api/auth/`, `api/telemetry/` and `api/stripe/webhook/` is built with `userRoute` (`require-user.ts`): session, then `Origin` on writes, `private, no-store`. `every-route.workers.test.ts` fails a route that skips it. Request bodies are read capped (`http.ts`) and checked with zod (`library-input.ts`). WAVs live in R2 at `users/{userId}/{recordings|toots}/{id}.wav`, keyed only by the session's user and a checked id, and each is written once (`If-None-Match: *`). The `workers` tests replace `session-user.ts` with a real `session` row (`test-support/workers-session.ts`); `signed-in.workers.test.ts` signs in for real.
- `src/lib/telemetry/`, `src/app/api/telemetry/`: error reports (`reportError(code, error)`, a stable code and an allowlist, logged by the route), the app's only telemetry, off with Profile's switch or Global Privacy Control (#126). `/dev/telemetry/` sends a synthetic crash and handled error, except in Production.
- `src/server/`: sign-in (#152), server-only behind `auth.ts`: Better Auth email codes (`create-auth.ts`, `auth-request.ts`, `auth-session.ts`), the limits every route shares in D1 (`rate-limits.ts`), email and the dev mailbox (`email.ts`, `dev-mailbox.ts`, `/dev/mail/`) ([Accounts and sign-in](docs/agents/accounts.md)).
- `src/components/farty/`: the screens, and the app's state in focused providers, which `farty-provider.tsx` nests: Welcome, what plays (`playback-provider.tsx`), the Song Catalog (`song-catalog-provider.tsx`), the Recordings and their Recording Analysis (`recordings-provider.tsx`), the Toots (`toots-provider.tsx`) and the record flow (`record-flow-provider.tsx`). Each context changes only with what it holds, so a screen re-renders only for the state it reads. `src/components/ui/` is shadcn's, kept as shadcn writes it, less what nothing uses.
- `worker.ts`: the Worker's entry, which answers the host redirects and the Staging gate before Next.js sees a request.

## Layers

Imports point inward, and each rule says what enforces it:

| Rule | Enforced by |
| --- | --- |
| `src/lib` holds the app's logic and never imports components, hooks or routes | Biome's `noRestrictedImports` in `apps/web/biome.json` |
| Components and hooks never import routes (`src/app`) | The same |
| The Song Catalog's Songs stay out of the browser's JavaScript: only routes and the server import `song-index.generated.ts`, and only tests `test-support/songs.generated.ts` | The same |
| Server code (`src/server`, `src/db/index.ts`) never reaches the browser | `import 'server-only'` in each entry, and Biome keeps `src/lib` from importing `src/server` and `src/db` |
| Server code never imports components, hooks or routes | Biome's `noRestrictedImports` |
| Production code imports no test or test support, and no devDependency | The dependency check (`verify.json`, the `apps/web` part) |
| No import cycles, and every module is reachable from an entry point | The same |
| `src/lib/analysis` and `src/lib/engine` use no DOM or Web Audio, so they run in a Web Worker and in Vitest | Biome's `noRestrictedGlobals` there (`window`, `document`, `navigator`, `localStorage`, `AudioContext`, `OfflineAudioContext`) |
