# Sharing, friends and reports

How sharing by unlisted link (ADR 0020), friends and profile pages (ADR 0021) work on the server, and how the owner handles a report. What a person sees is in the product docs: [Sharing](../../apps/web/docs/product/sharing.md), [Friends and profile pages](../../apps/web/docs/product/friends.md) and [Get Farty](../../apps/web/docs/product/get-farty.md).

## Sharing

- **Nothing is public until its owner shares it.** The owner's routes are under `src/app/api/` and built with `userRoute`: their Handle (`api/handle/`) and sharing or stopping sharing one of their own Recordings or saved Toots (`api/share/`). The public routes live outside `api/`: under `src/app/u/[handle]/r/[id]/` for a Recording and `t/[id]/` for a Toot, the page, its link image, its audio and its Report, which anyone with the link reaches. They're built with `publicRoute` and `reportRoute` (`src/server/public-route.ts`).
- **A link works only while its share is live.** Every request finds the item by joining `shares` to the owner's Handle and to the live item, in D1, so Stop sharing, deleting the item, deleting the account or a take-down ends the link at once. A Toot is in `toots` only once it's saved, so an unsaved Toot's link is never found. A Toot also stays down while any Recording it plays (in its Arrangement or its Sound Pad Performance) is taken down, so no Toot carries that Recording's audio back out. Every way a link stops working looks the same: a 404.
- **Links** are `/u/<handle>/r/<id>/` and `/u/<handle>/t/<id>/`. The id is 12 random characters of Crockford's lowercase base 32 (60 bits), so one link can't be guessed from another, and it says nothing about the item's own id. An item already shared keeps its link (`addShare`); Stop sharing deletes the share, so sharing again makes a new link. A link's Handle is checked by its shape only, lowercased, so a Handle the block list gained since it was picked still finds its links and its profile page.
- **Handles** (`src/lib/handle.ts`) are 3 to 20 characters of `[a-z0-9_]`, unique, and not on the block list, which catches digit-for-letter swaps and `_`. `claimHandle` gives a user their Handle once, in one statement, so two claims at once can't both win. The first one offered is made from the user's email, when it's free.
- **The owner's answers.** `PUT /api/handle/` answers 400 `handle_unusable` with the problem, 409 `handle_taken`, or 409 `has_handle` with the user's own. `PUT /api/share/{kind}/{id}/` answers 201 for a new link and 200 for the one the item has; 409 `no_handle` before the user has a Handle, 404 when the item isn't on their account (not uploaded yet, or someone else's), 410 when it was deleted, and 403 `taken_down` when Farty took it down, or, for a Toot, a Recording it plays. `DELETE` answers 204 whether or not it was shared. Deleting a Recording or a Toot also stops sharing it.
- **The pages** are `force-dynamic`, read from D1 on every request. They have no `loading.tsx`, because a streamed page would answer 200 before `notFound()` could make it a 404. They're unlisted: `robots` is noindex, nofollow, and `canonical` is null, which the root layout would otherwise give them. The page, its metadata and its link image share one lookup a request (React's `cache`). The service worker never handles `/u/`, so no copy of a stopped link's page opens. A shared page never shows an account id, an email, the item's own id or a Toot's id, in the HTML or its page data. It answers `private, no-cache`, so a link that stops working stops at once; Next adds `no-store` and the rest to a 404 of its own. D1 binds at most 100 values a statement, so the lookups by many ids go 90 at a time (`IN_BATCH` in `src/db/sharing.ts`), one value being the user id.
- **Shared audio** (`src/server/shared-audio.ts`). A Recording's link serves only the part its page plays: the handles of its stored Trim whenever it has one, whatever analysis found since, or else the whole take. So a Re-scan never makes public the audio its owner cut off. The part is a WAV of its own: the frames it covers read from R2 as a range, under a fresh header (`wavHeaderOf`), so nothing outside it is read or served. A Toot's is its saved WAV, whole. Each request checks the share in D1 first, then reads this data center's cache, or R2 into it. The cache key is the R2 key, which is written once, plus for a Recording the part, so a changed Trim never serves the old cut. The browser revalidates every time (`private, no-cache`, with the ETag; 304 when it has it), and nothing between keeps it. The Workers cache isn't there in `next dev`.
- **A Toot's bars** (60, for its page and link image) are drawn from its saved WAV and kept in this data center's cache by R2 key; they're flat when the audio is gone. A Toot longer than 480,000 frames is read every few frames, which draws the same bars for a fraction of the work.
- **Link previews** (`src/server/link-preview.tsx`): the page's Open Graph and Twitter tags and a 1200×630 image in Farty's pink, for a Recording's page and a Toot's alike. Both are drawn from D1 on each request, and the image isn't kept anywhere (`private, no-cache`), so a link that stops working takes its preview with it. Previews need the image's absolute URL, so `metadataBase` is the environment's own origin (`pageOrigin()`), or the request's on a local run, which has no host of its own. Satori draws the image, through `next/og`'s `ImageResponse`, and takes only a plain `<img>` ([Exceptions](exceptions.md)). The icon comes from the Worker's own files (`ASSETS`), and there's none in `next dev`. The bundled font has no ♯ and would fetch one from Google Fonts, so a sharp is spelled "#".

## Friends and profile pages

- **Requests** (`src/server/friends.ts`, `src/db/friends.ts`, under `src/app/api/friends/` with `userRoute`). A user asks another by their Handle, from that user's page or Profile's Add friend. Every route and query acts only between the signed-in user and the Handle in it, so nobody reaches a request or friendship between two others: that answers 404 `not_found`. A sender needs a Handle first, since whoever they ask sees them by it (409 `no_handle`). Asking someone who already asked accepts theirs (200 `friends`). Each request is one statement, so two at once, each way, can't both be made, and when the insert finds things changed since the read, it settles on the state after. Accepting makes the friendship, a row each way in `friends`, and deletes every request between the two, in one D1 batch. Declining and removing tell no one. Get Farty (#318) sends its request through the same `requestFriend`, once the new user has a Handle.
- **Profile pages** (`/u/<handle>/`, `src/server/profiles.ts`, `src/db/profiles.ts`) list only what their user shares now, Recordings and Toots together (#346), newest first and by link id when two were shared at once. Whatever its own link wouldn't show isn't listed: a stopped or taken-down share, a deleted item or account, or a Toot that plays a Recording Farty took down. Each item has its link, its name, and a Recording's note or a Toot's Song ("Sound Pad" for a Sound Pad Toot, nothing for a Song no longer in Farty). The time it was shared goes out in ms, so the page says "Today" in the viewer's own time zone.

## Limits

- **Every limit lives in D1's `rate_limit` table,** since each Worker isolate has its own memory: sign-in's, Report's (`REPORT_LIMITS` in `src/server/reports.ts`), friend requests' (`FRIEND_REQUEST_LIMITS` in `src/server/friends.ts`) and payments'. A request spends a slot of each limit it's under only when every one has a slot left, in one statement (`consumeSlots` in `src/server/rate-limits.ts`), so a request one limit refuses spends no other's. That works because SQLite reads the whole SELECT before it writes a row. Each row's window starts at its first slot, and every spend first deletes the rows whose window has ended.
- **Keys** are a label and an HMAC under the environment's sign-in secret (`authSecret()` in `src/server/auth.ts`): of the reporter's `cf-connecting-ip`, the sender's user id, or the pair; or a shared item's owner and id. Never an email or an address. Where there's no sign-in secret there are no reports (503 `unavailable`) and no friend requests. Every Report answer is `private, no-store`.
- **Reports:** 10 an hour per reporter, 5 a day per item, whichever link it's shared under, so sharing it again doesn't start them over, and 300 an hour for the site. Recordings, Toots and profile pages count together for the reporter and the site, and each profile page has its own 5 a day. Past any of them a report answers 429 `too_many_reports`.
- **Friend requests:** 20 an hour per sender, so no one can ask every Handle, and 3 in 30 days to the same person, so asking again after a decline can't become a stream of requests. Past either, 429 `too_many_requests`.

## Reports and take-downs

A shared Recording's or Toot's page has Report (#316, #317). Each report is a row in D1's `share_reports` (the share, its owner, the item and when; nothing about who reported) and a `share_reported` line in the Worker's logs with the link's id and kind: query `event = share_reported`, or read the table. Nobody is emailed.

**The owner takes one down** in the Cloudflare dashboard, under D1, `pedos-production` (or `pedos-staging`), Console. Agents never write to a remote database.

```sql
-- Newest reports first, with the link to open for each.
SELECT r.created_at, r.kind, r.item_id, r.share_id,
  '/u/' || h.handle || CASE r.kind WHEN 'toots' THEN '/t/' ELSE '/r/' END || r.share_id || '/' AS link
  FROM share_reports r JOIN handles h ON h.user_id = r.user_id
  ORDER BY r.created_at DESC LIMIT 20;
-- Take one down: its page, image, audio and Report answer 404 from the next request.
UPDATE shares SET taken_down_at = unixepoch() * 1000 WHERE id = '<share_id>';
```

The link to open is `/u/<handle>/r/<share_id>/` for a `recordings` report and `/u/<handle>/t/<share_id>/` for a `toots` one.

**What a take-down covers.** The item behind that one share. A link taken down stays down: its row is kept, so the owner can't share that Recording or Toot again (403 `taken_down`), and neither Stop sharing nor deleting it removes it. Taking down a Recording also takes down every Toot that plays it (in its Arrangement or its Sound Pad Performance): those Toots' links answer 404 at once, they drop out of the owner's shares and profile page, and sharing one again answers 403 `taken_down`. Taking down a Toot covers only that Toot, not the Recordings it plays. To put a link back, set `taken_down_at` to `NULL`; the Toots that play a Recording come back with it. Deleting the account removes it, with the reports.

A profile page, `/u/<handle>/`, has Report too (#319): a `profile_reports` row (the user and when, never the reporter) and a `profile_reported` log line with the Handle. A page lists only live shares, so taking down each of its shares empties it. There's no way yet to take a Handle away.

```sql
-- Newest profile reports first, and what each page lists.
SELECT r.created_at, h.handle, r.user_id FROM profile_reports r
  JOIN handles h ON h.user_id = r.user_id ORDER BY r.created_at DESC LIMIT 20;
SELECT id, kind, item_id FROM shares WHERE user_id = '<user_id>' AND taken_down_at IS NULL;
```
