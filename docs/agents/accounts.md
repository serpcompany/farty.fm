# Accounts and sign-in

How a person signs in to the web app, and what agents may do with accounts. Environments and deploys are in [the web app guide](web.md).

- **Sign-in (#152).** Better Auth email codes on D1 (`src/server/create-auth.ts`, with the request guard in `auth-request.ts`, the hooks in `auth-hooks.ts`, the settings in `auth-settings.ts` and the limits in `rate-limits.ts`, none of which import Next.js, so their tests run them on a real local D1; `src/server/auth.ts` is the server-only entry, with `getSessionUser(request)`, which reads D1 on every call and throws `AuthUnavailableError` when sign-in isn't set up; `src/server/session-user.ts` hands it to the library routes, which answer 401 signed out and 503 then). Account delete deletes the user's WAVs, then their row with their waiting sign-in codes (`verification`, named by the lowercased email), then their WAVs again, for an upload already past its session check; their sessions go with the row (`on delete cascade`). `/api/auth/*` serves only send code, sign in with code, get session and sign out; everything else there is a 404. Codes are 6 digits, live 10 minutes, allow 3 guesses and are kept only as an HMAC under `BETTER_AUTH_SECRET`; sessions last 7 days. Writes must come from the environment's own origin as JSON, at most 16 KB, checked before Better Auth, whose own origin and CSRF checks are also forced on (it skips them under `NODE_ENV=test`). Rate limits live in D1's `rate_limit` table, keyed by HMACs, never an email or IP address: per client (`cf-connecting-ip`, IPv6 by /64) by Better Auth, with a 429; sign-in guesses at 60 an hour per client; and codes at 5 an hour per email and client, 30 an hour per network (an IPv4 address, or an IPv6 /48, since one holder of a /48 has 65,536 /64s), 20 an hour per email and 300 an hour site-wide, each answered like a sent code so nothing says whether an account exists (`LIMITS` in `rate-limits.ts`). They are spent in that order, each only when the ones before allow it, with Staging's allowlist before the site's count, so one client can't spend an email's codes, a network past its 30 can't spend anyone's codes per email, one network can take at most a tenth of the site's, and the site counts only codes that go out. Better Auth swallows delivery errors, so a code request where email goes nowhere answers 503 before any limit is spent. Once the site's 300 are spent, nobody gets a code until that hour's window ends, and each code request it holds logs one `auth_site_code_limit` line in the Worker's logs, with the limit and the seconds left and no email, client or key. Email goes out through the `EMAIL` `send_email` binding from `support@farty.fm` (`src/server/email.ts`), and Staging's binding sends only to `STAGING_SIGNUP_ALLOWLIST`, which is also the only list Staging signs up. A local run (no `SITE_ENV`) sends nothing: each email lands in the `DEV_MAILBOX` KV, listed at `/dev/mail/`, which answers 404 anywhere but a local run on a local host. So sign-in works on `pnpm dev` and on a preview with no `--env`, and answers 503 on a preview with `--env`, which has no secret and the branded origin. `BETTER_AUTH_SECRET` is a Worker secret set once per environment by `.github/workflows/web-auth-secret.yml` (`gh.sh workflow run web-auth-secret.yml --ref staging -f environment=staging`, or `--ref main` and `production`); until then that environment's sign-in answers 503. A local run without one makes its own for the process.
- **Agents never sign in on Production.** Agents never create an account or sign in on Production (https://farty.fm, www.farty.fm). They use Staging for sign-in tests.
