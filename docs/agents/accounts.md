# Accounts and sign-in

How a person signs in to the web app, and what agents may do with accounts. Environments and deploys are in [the web app guide](web.md).

- **Sign-in (#152).** Better Auth email codes on D1 (`src/server/create-auth.ts`, with the request guard in `auth-request.ts`, the hooks in `auth-hooks.ts`, the settings in `auth-settings.ts` and the limits in `rate-limits.ts`, none of which import Next.js, so their tests run them on a real local D1; `src/server/auth.ts` is the server-only entry, with `getSessionUser(request)`, which reads D1 on every call and throws `AuthUnavailableError` when sign-in isn't set up; `src/server/session-user.ts` hands it to the library routes, which answer 401 signed out and 503 then). Account delete deletes the user's WAVs, then their row with their waiting sign-in codes (`verification`, named by the lowercased email), then their WAVs again, for an upload already past its session check; their sessions go with the row (`on delete cascade`). `/api/auth/*` serves only send code, sign in with code, get session and sign out, and Farty's own `GET /api/auth/turnstile` (below); everything else there is a 404. Codes are 6 digits, live 10 minutes, allow 3 guesses and are kept only as an HMAC under `BETTER_AUTH_SECRET`; sessions last 7 days. Writes must come from the environment's own origin as JSON, at most 16 KB, checked before Better Auth, whose own origin and CSRF checks are also forced on (it skips them under `NODE_ENV=test`). Rate limits live in D1's `rate_limit` table, keyed by HMACs, never an email or IP address: per client (`cf-connecting-ip`, IPv6 by /64) by Better Auth, with a 429; sign-in guesses at 60 an hour per client; and codes at 5 an hour per email and client, 30 an hour per network (an IPv4 address, or an IPv6 /48, since one holder of a /48 has 65,536 /64s), 20 an hour per email and 300 an hour site-wide, each answered like a sent code so nothing says whether an account exists (`LIMITS` in `rate-limits.ts`). They are spent in that order, each only when the ones before allow it, with Staging's allowlist before the site's count, so one client can't spend an email's codes, a network past its 30 can't spend anyone's codes per email, one network can take at most a tenth of the site's, and the site counts only codes that go out. Better Auth swallows delivery errors, so a code request where email goes nowhere answers 503 before any limit is spent. Once the site's 300 are spent, nobody gets a code until that hour's window ends, and each code request it holds logs one `auth_site_code_limit` line in the Worker's logs, with the limit and the seconds left and no email, client or key. Email goes out through the `EMAIL` `send_email` binding from `support@farty.fm` (`src/server/email.ts`), and Staging's binding sends only to `STAGING_SIGNUP_ALLOWLIST`, which is also the only list Staging signs up. A local run (no `SITE_ENV`) sends nothing: each email lands in the `DEV_MAILBOX` KV, listed at `/dev/mail/`, which answers 404 anywhere but a local run on a local host. So sign-in works on `pnpm dev` and on a preview with no `--env`, and answers 503 on a preview with `--env`, which has no secret and the branded origin. `BETTER_AUTH_SECRET` is a Worker secret set once per environment by `.github/workflows/web-auth-secret.yml` (`gh.sh workflow run web-auth-secret.yml --ref staging -f environment=staging`, or `--ref main` and `production`); until then that environment's sign-in answers 503. A local run without one makes its own for the process.
- **Deleting an account needs a recent sign-in.** `DELETE /api/account/` needs a sign-in less than 10 minutes old (`RECENT_SIGN_IN_MINUTES` in `src/server/auth-session.ts`), so a phone left signed in can't delete the account: an older one gets 403 `sign_in_again` and nothing is deleted. The age is the session's `createdAt`, which `getSessionUser` hands on as `signedInAt`: Better Auth 1.7.7 sets it at sign-in, and renewing a session (`updateAge`) moves only `expiresAt` and `updatedAt`. Better Auth's own `freshAge` makes the same check, but only inside its own endpoints (`delete-user`, `list-sessions`, `unlink-account`), none of which `/api/auth/*` serves, so the route checks directly. Profile answers the refusal with a new code (Turnstile included) and signs in with it, which makes a new session, then deletes with that one.
- **Turnstile on send code (#237, ADR 0013).** Sending a code needs a Cloudflare Turnstile token in `x-captcha-response` (Better Auth's `captcha` plugin, on send code only; signing in with the code needs nothing more). Without one it answers 400, and 403 when Cloudflare refuses it. It runs after Better Auth's per-client limit and before the code limits, which are unchanged. The account step renders the widget under the email (`src/components/farty/turnstile.tsx`), and Profile's Delete account in its new code step (`sign-in-code.tsx` holds what both share), with the site key from `GET /api/auth/turnstile`, so a build reads the key of the Worker it runs on. The Content-Security-Policy allows its script and its challenge frame from `https://challenges.cloudflare.com` (`src/lib/security-headers.ts`); without them the browser blocks the widget, and no code can be sent. Each environment's site key is public and is `TURNSTILE_SITE_KEY` in its `vars` in `wrangler.jsonc` (Cloudflare widgets "farty.fm Staging sign-in" and "farty.fm Production sign-in"). `TURNSTILE_SECRET_KEY` is a Worker secret, set on both Workers by the owner (2026-10-28). A deployed environment without both sends no code (503 `TURNSTILE_UNAVAILABLE`, with an `auth_unavailable` log line, reason `turnstile_missing`) and still reads sessions. A local run (no `SITE_ENV`, CI's e2e included) uses Cloudflare's published test keys: the top level's `vars`, and the test secret (`TURNSTILE_TEST_SECRET_KEY`) unless `.dev.vars` sets `TURNSTILE_SECRET_KEY`. The test widget always passes and gives the token `XXXX.DUMMY.TOKEN.XXXX`, which the e2e journeys send when they sign in by API (`TURNSTILE_TEST_TOKEN` in `e2e/account.ts`).
- **How much an account keeps.** At most 300 Recordings and 300 Toots, with a Recording's WAV at most 6 MB and a Toot's 16 MB: `LIMITS` in `apps/web/src/server/library.ts`, the one place to change them, the same in every environment. Uploads (`putItem`) read it, and so does the Toot checkout (`startCheckout` in `toot-payments.ts`), which takes no payment for a Toot past the count; an upload past it answers 409 `limit_reached`. Changing a count changes only what the server accepts next: lowering it deletes nothing, it refuses uploads until an account is under. A browser holds back an upload the account refused as full until a delete, another browser's delete, a new session or the next open ([ARCHITECTURE.md](../../ARCHITECTURE.md#the-web-apps-layout), `library-sync.ts`), so a raised count reaches waiting farts the next time Farty opens. The screens never print the counts; the Workers tests (`library-uploads.workers.test.ts`, `payments.workers.test.ts`) and the product docs ([Accounts](../../apps/web/docs/product/account.md#sync), [Recordings](../../apps/web/docs/product/recordings.md#a-full-account), [Toots](../../apps/web/docs/product/toots.md#a-full-account), [Paying to save a Toot](../../apps/web/docs/product/payments.md)) say 300 and change with it.
- **Agents never sign in on Production.** Agents never create an account or sign in on Production (https://farty.fm, www.farty.fm). They use Staging for sign-in tests.
