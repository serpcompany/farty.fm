# Web app: working guide

How `apps/web` is built, deployed and checked. Its commands are in `apps/web/AGENTS.md`.

## Environments and deploys

- **Branches.** `staging` is the base and default branch: every branch starts from it, and every PR goes into it. `main` is Production. It changes only by promotion from `staging` and by its release PR (see Promotion and Releases, below), never by a PR from a work branch.
- **Environments.** One Worker per deployed environment, set under `env` in `apps/web/wrangler.jsonc`. Its top level is local-only and never deployed. Each build bakes in `SITE_ENV`, so a build serves only the environment it was built for.

  | Environment | Worker | URL | Build |
  | --- | --- | --- | --- |
  | Local | none | http://localhost:3000 (`pnpm dev`) | `pnpm build`, inside `pnpm check` |
  | Staging | `pedos-web-staging` | https://staging.farty.fm | `pnpm build:staging` |
  | Production | `pedos-web-production` | https://farty.fm | `pnpm build:production` |

- **Data (#150).** Each deployed environment binds its own D1 as `DB` and its own R2 bucket as `MEDIA`, both named `pedos-staging` or `pedos-production`, in the SERP Cloudflare account. The top level binds `pedos-local` (database id `local-only-do-not-deploy`), kept in `.wrangler/`, and the dev mailbox KV `DEV_MAILBOX`, which no deployed environment has. Drizzle owns every table, Better Auth's too (`src/db/schema.ts`). `pnpm db:generate` writes each change's migration into `drizzle/`, and `pnpm db:migrate:local` applies them locally. Remote databases change only through CI, never from an agent's machine. `src/db/deploy-config.test.ts` fails if `DEV_MAILBOX` reaches a deployed environment, a deploy or remote migration lacks `--env`, or an environment's hosts, `BETTER_AUTH_URL` or sender disagree with `site.ts` and `SUPPORT_EMAIL`.
- **Sign-in (#152).** Better Auth email codes on D1 (`src/server/auth-config.ts`; `src/server/auth.ts` is the server-only entry, with `getSessionUser(request)`, which reads D1 on every call and throws `AuthUnavailableError` when sign-in isn't set up; `src/server/session-user.ts` hands it to the library routes, which answer 401 signed out and 503 then). Account delete also deletes the user's waiting sign-in codes (`verification`); their sessions go with the user's row (`on delete cascade`). `/api/auth/*` serves only send code, sign in with code, get session and sign out, and Farty's own `GET /api/auth/turnstile` (below); everything else there is a 404. Codes are 6 digits, live 10 minutes, allow 3 guesses and are kept only as an HMAC under `BETTER_AUTH_SECRET`; sessions last 7 days. Writes must come from the environment's own origin as JSON, at most 16 KB. Rate limits live in D1's `rate_limit` table, keyed by HMACs, never an email or IP address: per client (`cf-connecting-ip`, IPv6 by /64) by Better Auth, with a 429; sign-in guesses at 60 an hour per client; and codes at 5 an hour per email and client, 20 an hour per email and 300 an hour site-wide, each answered like a sent code so nothing says whether an account exists (`LIMITS` in `auth-config.ts`). Once the site's 300 are spent, nobody gets a code until that hour's window ends, and each code request it holds logs one `auth_site_code_limit` line in the Worker's logs, with the limit and the seconds left and no email, client or key. Email goes out through the `EMAIL` `send_email` binding from `support@farty.fm` (`src/server/email.ts`), and Staging's binding sends only to `STAGING_SIGNUP_ALLOWLIST`, which is also the only list Staging signs up. A local run (no `SITE_ENV`) sends nothing: each email lands in the `DEV_MAILBOX` KV, listed at `/dev/mail/`, which answers 404 anywhere but a local run on a local host. So sign-in works on `pnpm dev` and on a preview with no `--env`, and answers 503 on a preview with `--env`, which has no secret and the branded origin. `BETTER_AUTH_SECRET` is a Worker secret set once per environment by `.github/workflows/web-auth-secret.yml` (`gh.sh workflow run web-auth-secret.yml --ref staging -f environment=staging`, or `--ref main` and `production`); until then that environment's sign-in answers 503. A local run without one makes its own for the process.
- **Turnstile on send code (#237, ADR 0013).** Sending a code needs a Cloudflare Turnstile token in `x-captcha-response` (Better Auth's `captcha` plugin, on send code only; signing in with the code needs nothing more). Without one it answers 400, and 403 when Cloudflare refuses it. It runs after Better Auth's per-client limit and before the code limits, which are unchanged. The account step renders the widget under the email (`src/components/pedos/turnstile.tsx`) with the site key from `GET /api/auth/turnstile`, so a build reads the key of the Worker it runs on. Each environment's site key is public and is `TURNSTILE_SITE_KEY` in its `vars` in `wrangler.jsonc` (Cloudflare widgets "farty.fm Staging sign-in" and "farty.fm Production sign-in"). `TURNSTILE_SECRET_KEY` is a Worker secret, set on both Workers by the owner (2026-10-28). A deployed environment without both sends no code (503 `TURNSTILE_UNAVAILABLE`, with an `auth_unavailable` log line, reason `turnstile_missing`) and still reads sessions. A local run (no `SITE_ENV`, CI's e2e included) uses Cloudflare's published test keys: the top level's `vars`, and the test secret in `auth-config.ts` unless `.dev.vars` sets `TURNSTILE_SECRET_KEY`. The test widget always passes and gives the token `XXXX.DUMMY.TOKEN.XXXX`, which the e2e journeys send when they sign in by API (`TURNSTILE_TEST_TOKEN` in `e2e/account.ts`).
- **Payments (#204, ADR 0010).** Saving a Toot costs `TOOT_PRICE` (`src/lib/pricing.ts`), paid through Stripe Checkout, which Stripe hosts. `POST /api/toots/{id}/checkout/` starts a Checkout Session for one Toot (or reuses the open one) and records it, with its Song, in `toot_payments`, and Checkout returns to that Song's Song Creator; for a Sound Pad Toot (`songId: null`, ADR 0017) the row has no Song and Checkout returns to `/compose/pad/`; when another Toot of the same Song is paid and was never saved (the page closed before the return), it answers `{ paidToot }` and Song Creator saves that one instead of paying twice, which a Sound Pad Toot never does; `POST /api/stripe/webhook/` checks `Stripe-Signature` with `STRIPE_WEBHOOK_SECRET` and marks the Toot paid on `checkout.session.completed` or `checkout.session.async_payment_succeeded`; `GET /api/toots/{id}/payment/` asks Stripe too, so the return from Checkout doesn't wait on the webhook, and answers `{ paid, unused }`: `unused` while the Toot's own payment is paid and no save has used it, which is when the Sound Pad, opened after a return that never loaded, makes a kept take again and saves it (never with saving free). The Sound Pad's check on open adds `?check=stored`, which answers from D1 alone and never asks Stripe, so it spends none of the return's Stripe checks. `PUT /api/toots/{id}/` answers 402 `payment_required` for a new Toot that isn't paid, and its first save uses the payment up (`saved_at`), so a deleted paid Toot answers 410 even after its tombstone is purged. A paid session counts only for the amount and currency its Toot's payment row recorded when the checkout started (`TOOT_PRICE` then), so a payment made before a price change still counts. With Adaptive Pricing, the session still records that price and the buyer's own currency is in `presentment_details`, so it counts too. A Toot whose last session is paid at any other price answers 409 `payment_mismatch` (logged as `stripe_paid_session_refused`) and never starts a second payment. Each user may start 20 checkouts an hour (then 429 `rate_limited`) and have the payment check ask Stripe 60 times in 10 minutes (then it answers from D1, which the webhook keeps). The Worker calls Stripe with `fetch` (`src/server/stripe.ts`), with no SDK, on a pinned API version (`STRIPE_API_VERSION`) and with an idempotency key on each new session. `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` are Worker secrets the owner sets from their own terminal (Stripe, below), never in `wrangler.jsonc`. Production takes only live keys (`sk_live_`, `rk_live_`) and live events; Staging and local runs only test keys (`sk_test_`, `rk_test_`) and test events. Without a key of its mode, an environment where saving is paid answers 503 `payments_unavailable`, which Save shows. A local run on a local host with no key uses the dev checkout (`/dev/checkout/`, and `POST /api/dev/checkout/`, which marks a started checkout paid), for the journeys and tap-throughs; both answer 404 anywhere else. Saving is paid everywhere: Production in live mode since #258 (2026-10-28), and so is a Production build run locally (`builtFor()`), on both the browser's and the server's side, through the dev checkout when it has no key. `savingIsPaid` (`src/lib/pricing.ts`) is the one switch: putting `'production'` back in its `FREE_SAVING` makes Production save free again (the `free` kind of `Payments`), say if live payments break. The owner's Stripe steps are in Stripe, below.
- **Branded hosts.** Each environment's host is a custom domain in its `routes` in `wrangler.jsonc`, and Production also takes `www.farty.fm`. The Worker entry (`apps/web/worker.ts`, with `src/lib/other-hosts.ts`) answers `www.farty.fm` with a 308 to `https://farty.fm`, and each Worker's `*.workers.dev` host with a 308 to its environment's host. Each is one hop that keeps the path (in Next's trailing-slash form) and the query. A workers.dev request with the `x-pedos-smoke-test` header is served instead, so CI's smoke test reaches the Worker even when Bot Fight Mode challenges the branded host. Production serves static files without the Worker (it doesn't set `run_worker_first`), so a static file on `www` or workers.dev is served there rather than redirected. Every environment sets `workers_dev: true` and `preview_urls: false`, so no preview URLs exist. The hosts from before the rename answer with a 301 to these from a redirect rule on their own Cloudflare zone, outside the Worker (ADR 0009).
- **Canonicals, robots and sitemaps** name each environment's own host, from `src/lib/site.ts`. The layout sets `metadataBase` and each page's canonical (the home page's is the bare origin, with no slash). `/sitemap-index.xml` lists `/sitemap-pages.xml`, which lists the public pages: `/`, `/privacy/` and `/support/`. Production's `robots.txt` allows every crawler. Staging's disallows every crawler except `AhrefsSiteAudit`, which gets Production's rules so a site audit given the password can crawl Staging as it would Production. Both list their own sitemap index. A local build disallows everything and lists no sitemap.
- **CI.** `.github/workflows/web.yml` runs on every PR and on every push to `staging` and `main`:
  - `changes`: on a PR, whether anything the web app builds from changed (`apps/web`, `fixtures`, `catalog` or the workflow). When nothing did, `check` and the e2e shards skip their steps and still report. On a push, it also looks up the `passed-e2e-<tree>` receipt, so every shard agrees on whether the journeys run.
  - `check`: ShellCheck on the smoke test, lint, types (with `wrangler types --check`), `drizzle-kit check`, a guard that fails when `pnpm db:generate` would write a migration (a `schema.ts` change without its migration), and unit tests. On a PR it also runs both Workers builds: `build:production`, which fails if the build carries any Fixture Library file, and `build:staging`, which `check` runs only on a draft, since the e2e shards build it otherwise. On a push, the deploy job's build is the build check.
  - `e2e shard 1` to `4` (`e2e-shard`, #337): the Playwright journeys on the Staging build in workerd, behind the gate, split four ways with `pnpm test:e2e --shard=<i>/4`. Each shard is its own job: it builds Staging, writes `.dev.vars` from `.dev.vars.example`, applies the migrations to its local database and runs its quarter of the journeys, one at a time as before. A failing shard uploads its own `playwright-report-<i>`. A draft PR skips them; they run when the PR is marked ready. Locally, `pnpm test:e2e` still runs every journey. Add a shard to the matrix when the slowest one nears 10 minutes.
  - `e2e`: the required check. It runs after the shards even when one failed or was cancelled, fails unless `changes` and every shard passed, and then uploads the run's one `passed-e2e-<tree>` receipt. A push whose tree already passed skips the journeys: the shards skip their steps, and `e2e` passes.
  - `deploy-staging` on a push to `staging`, and `deploy-production` on a push to `main`, each once `check` and `e2e` pass, in its GitHub environment. Each builds and, only when the commit is still the branch tip (an older run passes without deploying), applies its environment's migrations (`pnpm db:migrate:<env>`) and deploys, then runs `scripts/smoke.sh` on its workers.dev host. Each has its own group (`deploy-web-staging`, `deploy-web-production`): a running deploy is never cancelled, and a newer queued run replaces an older one. When no push started a run (for example, `web.yml` was off), `bash ~/.claude/skills/serp-github-app/scripts/gh.sh workflow run web.yml --ref staging` (or `--ref main`) checks and redeploys that branch's tip.
  - `staging` and `main` require `changes`, `check`, `e2e` and `issue-link` (`pr-issue-link.yml`). `ios.yml` isn't required: its `paths` filter would leave its check pending.
- **Each environment has its own token.** `CLOUDFLARE_API_TOKEN` is an environment secret in `staging` and in `production`, each a different token, and `CLOUDFLARE_ACCOUNT_ID` is a repository variable naming the SERP account, which `wrangler.jsonc` also names (`account_id`), so `wrangler` picks it on a machine whose login sees more than one account. If the two ever differ, `wrangler.jsonc` wins. Each environment's branch policy lets only its own branch deploy: `staging` from `staging`, `production` from `main`. Each token can edit every Worker in the account, so these policies are what keep other branches away from both tokens. With no token the deploy fails, so a green run at the tip always deployed and passed the smoke test. Since each is account-wide, making or rolling one is the owner's ([Secret Authority](https://github.com/serpcompany/serp/blob/main/docs/engineering/standards/agent-operations/secret-authority.md)). The owner's keychain minter makes only tokens scoped to one project ([Cloudflare API tokens](https://github.com/serpcompany/serp/blob/main/docs/engineering/standards/environment-configuration.md#cloudflare-api-tokens)).
- **Agents never sign in on Production.** Agents never create an account or sign in on Production (https://farty.fm, www.farty.fm). They use Staging for sign-in tests.
- **Web consoles use Claude in Chrome.** For web consoles (GitHub settings, the Cloudflare dashboard, App Store Connect) and owner-only dashboard steps, such as secret-value clicks, use Claude in Chrome (owner, 2026-10-06), not the built-in browser. GitHub actions themselves (issues, PRs, comments, merges, workflow runs) still go through serp-agent's `gh.sh`. Never read, type or print a secret there. A dashboard's key is the owner's to set from their own terminal ([Secret Authority](https://github.com/serpcompany/serp/blob/main/docs/engineering/standards/agent-operations/secret-authority.md)).
- **Deploys come only from CI.** The `deploy:*` scripts are for a person in an emergency; agents never run them, or `wrangler deploy`. To check a build in the Workers runtime without deploying, from `apps/web/`: `pnpm build:production`, then `pnpm exec opennextjs-cloudflare preview --env production --port <port>`, then `scripts/smoke.sh http://localhost:<port> production`. For Staging, the same with `build:staging`, `--env staging` and `staging`. A preview with `--env` rewrites `Host` to the custom domain, so it never shows the host redirects. Check those on a preview with no `--env`, sending `Host: www.farty.fm` or `Host: pedos-web-staging.serpcompany.workers.dev`.
- **Staging asks for a password.** The password is `stagingpassword`, with any username. It's public, so it's the plain variable `STAGING_BASIC_AUTH_PASSWORD` in `env.staging`, not a secret. The Worker entry (`apps/web/worker.ts`; the gate is `src/lib/staging-access.ts`) checks it after the host redirects and before anything is served, then strips `Authorization`. Staging sets `assets.run_worker_first`, so static files need it too. Only `/robots.txt`, Stripe's webhook (`POST /api/stripe/webhook/`, which checks Stripe's signature instead) and requests with the `x-pedos-smoke-test` header and no `Authorization` skip it. The Fixture Library under `/fixtures/` needs the password even with that header. Every response keeps `X-Robots-Tag: noindex` unless its request passed the password. Outside Production a missing variable refuses everything. Production has no gate.
- **Local runs pass the gate.** Copy `apps/web/.dev.vars.example` to `.dev.vars` (git-ignored). Local workerd runs (`opennextjs-cloudflare preview` with no `--env`) gate pages with it, and `E2E_SERVER=preview pnpm test:e2e` sends it with Playwright's `httpCredentials`, on `E2E_PORT`. `pnpm dev` has no gate. CI's e2e shards write `.dev.vars` the same way.
- **Only Staging carries the Fixture Library.** `build:staging` copies it to `public/fixtures/recordings/` and sets `NEXT_PUBLIC_FIXTURE_LIBRARY=1`, which shows its loader on Profile. `build:production` removes it, then `scripts/fixture-library.ts check` fails the build if it carries any file under a `fixtures/` path, any file identical to one in `fixtures/recordings/`, or the loader's text.
- **The smoke test** is `scripts/smoke.sh <base-url> staging|production`. On both, it checks the pages, icons and microphone policy, that `robots.txt` answers with no password and lists the sitemap index, and that the sitemaps name the environment's host. On Staging, a page and a static file refuse a wrong password (401 with `WWW-Authenticate`) and pass with `stagingpassword`, with no `noindex` and a canonical on `staging.farty.fm`. The header alone passes with `noindex`, the Fixture Library's index asks for the password even with the header, and `robots.txt` disallows `*` and gives `AhrefsSiteAudit` Production's rules. On Production, nothing asks for a password, even a wrong one, nothing has `noindex`, canonicals are on `farty.fm`, `robots.txt` allows crawling, and no Fixture Library is served. Off localhost, on both, `/dev/mail/` and `/dev/checkout/` answer 404, `/api/auth/get-session` answers 200 JSON and a malformed sign-in from the site gets a 400. The two sign-in checks need the environment's `BETTER_AUTH_SECRET`, so they fail (503) on a deploy that comes before `web-auth-secret.yml` has run there. A local preview's sign-in is the e2e journey's. On a workers.dev host, it also checks that a request without the header gets a 308 to the branded host, and checks the branded host itself (and `www` on Production). The branded-host checks skip with a `::warning::` when Bot Fight Mode challenges the runner.

### Promotion and releases

The `gh` and `git` commands here run as the organization's app, through the `serp-github-app` skill's `gh.sh` and `git.sh` ([Agent GitHub Identity](https://github.com/serpcompany/serp/blob/main/docs/engineering/standards/agent-harness/agent-github-identity.md)). A person runs plain `gh` and `git`. The rules are SERP's [git workflow](https://github.com/serpcompany/serp/blob/main/docs/engineering/standards/git-workflow.md#promoting-staging-to-production).

- **Promotion** fast-forwards `main` to `staging`'s tip, so Production gets exactly the squash commits Staging tested. The push to `main` deploys Production and smoke-tests it; a promoted tree usually has its receipt already, so the journeys skip. `main`'s pull-request rule lets only its bypass actors, the owner and the release workflow, push it, so the owner runs:

  ```sh
  git fetch origin && git push origin origin/staging:main
  ```

  If `main` has diverged (a hotfix landed there), open a `staging` → `main` PR instead and merge it with a merge commit, then merge back (below).
- **Releases.** Release Please (`.github/workflows/release-please.yml`, configured for `apps/web` in `release-please-config.json`) keeps one `release: Farty x.y.z` PR open on `main`, built from the commits that promotion brought. Merging it bumps `apps/web/package.json`, writes `apps/web/CHANGELOG.md` and tags `vX.Y.Z`. Nobody types versions or tags. The root `CHANGELOG.md` is the iPhone app's history, and `v1.0.0` is its release, so the web app's first release is `v1.1.0`.
- **A release PR gets its checks from a reopen.** Release Please opens and rewrites its PR with Actions' own `GITHUB_TOKEN`, which starts no workflows, so no check reports on it and `main` requires them. Right before merging, after the last push to `main`, close and reopen it as the app. That runs every required check, with none bypassed and no secret added. Once they pass, merge it:

  ```sh
  bash ~/.claude/skills/serp-github-app/scripts/gh.sh pr close <n>
  bash ~/.claude/skills/serp-github-app/scripts/gh.sh pr reopen <n>
  bash ~/.claude/skills/serp-github-app/scripts/gh.sh pr checks <n> --watch
  bash ~/.claude/skills/serp-github-app/scripts/gh.sh pr merge <n> --squash
  ```

- **Web releases roll forward, not back.** From #168 on, the library is IndexedDB version 3, from #268 version 4, from #277 version 5 (the Sound Pad's Pads), from #293 version 6 (a Recording's Trim, ADR 0019), from #313 version 7 (Favorite Songs), from #314 version 8 (a Recording's name and "No note"), and from #360 version 9 (a Song's Fart Choices), which an older build can't open (`VersionError`), so a Cloudflare rollback past any of them breaks the library in every browser that opened the newer build. Version 4 is there so a build from before #268 never sends a queued `place` as a delete, version 6 so a build from before #293 never sends one without its Trim, version 7 so a build from before #313 never meets a queued Favorite Song, which would stop its sync, version 8 so a build from before #314 never sends a `place` without the name or plays a Recording left out with "No note", and version 9 so a build from before #360 never meets a queued Fart Choices change, which would stop its sync. A Worker rolled back past #278 (ADR 0017) breaks Sound Pad Toots for new pages: its `toToot` drops `performance`, so a Pad Toot's screen can't read its taps, and it answers 400 to a checkout or save with a null `songId`, so the Sound Pad can't save. Migration 0005 can't be undone without losing Pad Toots either, since the old `toots` table holds `song_id NOT NULL`. Fix forward with a new release instead, and say so in a release PR's Merge Danger.
- **Merge `main` back into `staging`** at once after a release PR, a hotfix or a diverged promotion, so the next promotion still fast-forwards. It's a `main` → `staging` PR merged with a merge commit; a squash leaves `main` diverged. Open it before anything else merges into `staging`: its head is `main`, so it can't be brought up to date. `issue-link` exempts it. If something merged into `staging` first, close that PR and branch from `main` instead: merge `origin/staging` into the branch and open the branch → `staging` with a `No issue:` line, still merged with a merge commit. The branch's diff against `staging` should be only what `main` has and `staging` lacks, such as the version bump and changelog (#244).

  ```sh
  bash ~/.claude/skills/serp-github-app/scripts/gh.sh pr create --base staging --head main \
    --title "chore: merge main back into staging" --body "Brings the release commit from main to staging."
  bash ~/.claude/skills/serp-github-app/scripts/gh.sh pr merge <n> --merge
  ```

- **A change the release left out.** When a release PR leaves out a change that's on `main`, check whether it merged into `staging` before the merge-back. If so, the branch-from-`main` route above brought it to `main` only inside merge commits, and Release Please doesn't see it (#301 inside #306). To bring it back, add an override to the merged merge-back PR's body with the missing commit's squash subject from `staging`, `(#n)` included. Then re-run the latest Release Please run on `main` (`gh.sh run rerun <id>`), since the workflow runs only on a push to `main`:

  ```text
  BEGIN_COMMIT_OVERRIDE
  fix(web): start a Pad where a Song starts its fart, not at room noise (#298) (#301)
  END_COMMIT_OVERRIDE
  ```

  The override stands for every commit in that PR, so the release PR lists the line once per merge commit. Before merging, remove the duplicates from `apps/web/CHANGELOG.md` on its `release-please--…` branch and from its body (#307).

- **Who merges.** Before the MVP, agents merge every PR as serp-agent: work PRs, release PRs and merge-back PRs. A work PR merges once a fresh review has no open blocking finding, the cited local `pnpm check` on its head is green and the required checks pass; a release or merge-back PR once the required checks pass. Agents also tap through user-visible changes themselves. The owner isn't asked to merge, review or tap through, only to choose between design options, to set the keys Secret Authority leaves to the owner, and for what the hard limits forbid. The owner allowed all of this on 2026-10-21 (#106). After the MVP, SERP's standard applies: merging a release PR publishes, so it needs the owner's explicit go-ahead, and the owner merges or arms every PR that no `Agents may merge` line covers.

## Tapping through

Before review, the author walks each user-visible change at phone size on the local Workers build behind the Staging gate. The [`verify-pedos-web`](../../.claude/skills/verify-pedos-web/SKILL.md) skill has the steps. In short, from `apps/web/`:

```sh
cp .dev.vars.example .dev.vars
pnpm build:staging
pnpm db:migrate:local
# The smoke test, on the preview with --env staging:
pnpm exec opennextjs-cloudflare preview --env staging --port 4109
bash scripts/smoke.sh http://localhost:4109 staging   # in another shell
# The journeys and the tap-through, on a preview with no --env, as CI's e2e runs them:
E2E_SERVER=preview E2E_PORT=4110 pnpm test:e2e
```

Run e2e and the tap-through on the preview with no `--env`. With `--env staging`, the preview has no `BETTER_AUTH_SECRET` and the branded origin, so sign-in answers 503 locally. Give each parallel agent its own ports. Production's paid save (`e2e/production-save.spec.ts`) runs only against a Production build, locally, by hand: CI's e2e shards build Staging, where the spec skips. Run it after any change to payments or saving: `pnpm build:production`, then `E2E_SERVER=preview E2E_SITE_ENV=production pnpm test:e2e production-save`. With no `--env` and no Stripe key, its Save goes to the dev checkout. After the merge, CI redeploys Staging from `staging`'s tip, and the same smoke test runs there.

## Exceptions to SERP's standards

One line each is in `apps/web/AGENTS.md`. The detail:

- **Agents tap through, not the owner and not a PR preview.** The standard's PR previews need `preview_urls` on, which Farty turns off. A `tap-through` label that deployed a PR to Staging (#124) is `later`. For who merges before launch, see Who merges, above.
- **Errors and analytics are Cloudflare's own (#126).** The standard's Sentry and GTM are not used, and nothing is sent to a third party. What remains of the standard holds: errors and analytics stay apart, error reports stop with the switch on Profile (on by default, kept in the browser) or Global Privacy Control, and the privacy page says what each collects and for how long.
  - **Errors.** `reportError(code, error)` (`src/lib/telemetry/errors.ts`) posts a stable code, the error's type name, the screen, the release (version and commit, from `next.config.ts`), the environment and how long it waited offline to `/api/telemetry/`; never a message, stack, audio, name, email or anything typed. Uncaught errors and rejections are reported too (`src/instrumentation-client.ts`). In Production the browser sends it without cookies (`credentials: 'omit'`); elsewhere it sends the Staging gate's password, which `fetch` counts as a credential too. The route takes at most 30 a minute per `cf-connecting-ip` (the `TELEMETRY_RATE_LIMIT` binding in `wrangler.jsonc`; 429 over it, and none without the binding), only this site's origin, JSON up to 1 KB and a known code with bounded fields (`report.ts`), reads no session, and logs one `client_error` line, which Workers Logs keeps up to 7 days: query `event = client_error` in the Worker's Logs. Offline, up to 20 reports wait in `localStorage` and go once the browser is online. No source maps are uploaded and no stack is sent.
  - **Analytics.** They come from Cloudflare's automatic Web Analytics, which inserts its own beacon into every page on farty.fm and staging.farty.fm at the edge (owner's decision, [#126](https://github.com/serpcompany/farty.fm/issues/126#issuecomment-6317955308)). The app loads no analytics script, has no analytics token, and the switch and Global Privacy Control don't affect it. Error reports are the only telemetry in the app.
  - **Testing it.** `/dev/telemetry/` (Staging and local runs; 404 in Production) sends a synthetic crash and handled error. `e2e/telemetry.spec.ts` checks what is sent, offline and opt-out; with `E2E_SITE_ENV=production` and `E2E_BASE_URL` on `opennextjs-cloudflare preview --env production` after `pnpm build:production`, it checks that the triggers' page is gone.

## Stripe

Saving a Toot is paid on Staging in Stripe's test mode, and on Production in live mode (ADR 0010, #258). The code is done; the account and its keys are the owner's.

**The owner, once, for Staging (test mode):**

1. In the Stripe Dashboard, with **Test mode** on, open **Developers → API keys** and create a restricted key with **Write** on **Checkout Sessions** (everything else None), or use the test secret key.
2. Open **Developers → Webhooks → Add endpoint**: URL `https://staging.farty.fm/api/stripe/webhook/`, events `checkout.session.completed` and `checkout.session.async_payment_succeeded`. Set the endpoint's API version to `2026-08-26.dahlia`, the version every request pins (`STRIPE_API_VERSION`), so the events and the return read a session in the same shape. 3. Set both on the Staging Worker (`pedos-web-staging`) from your own terminal in `apps/web/`. Each command asks for its value:
   - `pnpm exec wrangler secret put STRIPE_SECRET_KEY --env staging`, with the key from step 1;
   - the same with `STRIPE_WEBHOOK_SECRET`, with the signing secret from step 2.

   An agent then checks both by name with `wrangler secret list --env staging`. Never paste either value into chat.

Checkout asks for cards only (Apple Pay and Google Pay are cards), since a slower method would leave the Toot unsaved after the return. 5. Pay once on https://staging.farty.fm with Stripe's test card `4242 4242 4242 4242`, and check that the Toot shows as saved and the payment shows in the Dashboard.

**For Production (live mode, #258):** the same steps with **Test mode** off: a live restricted key, and a live webhook endpoint on `https://farty.fm/api/stripe/webhook/`, set on `pedos-web-production` with `--env production`. Done on 2026-10-28: the owner set both secrets, and an agent checked them by name with `wrangler secret list --env production`. The code takes only live keys and live events there (#213), and charges there since #258. Left for the owner, once a promotion has taken #258 to farty.fm: pay $0.99 once on https://farty.fm with a real card, refund it in the Dashboard, and check that the Dashboard shows the live payment and the webhook's delivery. Google Play's billing policy (#114) is settled before the Play app ships.

## Reports and take-downs

A shared Recording's or Toot's page has Report (#316, #317, ADR 0020). Each report is a row in D1's `share_reports` (the share, its owner, the item and when; nothing about who reported) and a `share_reported` line in the Worker's logs with the link's id: query `event = share_reported`, or read the table. Nobody is emailed. A reporter gets at most 10 an hour, a Recording or Toot 5 a day (whichever link it is shared under) and the site 300 an hour, Recordings and Toots counted together (`REPORT_LIMITS` in `src/server/sharing.ts`); past any of them a report answers 429.

**The owner takes one down** in the Cloudflare dashboard, under D1, `pedos-production` (or `pedos-staging`), Console. Agents never write to a remote database.

```sql
-- Newest reports first, with the link to open for each.
SELECT r.created_at, r.kind, r.item_id, r.share_id,
  '/@' || h.handle || CASE r.kind WHEN 'toots' THEN '/t/' ELSE '/r/' END || r.share_id || '/' AS link
  FROM share_reports r JOIN handles h ON h.user_id = r.user_id
  ORDER BY r.created_at DESC LIMIT 20;
-- Take one down: its page, image, audio and Report answer 404 from the next request.
UPDATE shares SET taken_down_at = unixepoch() * 1000 WHERE id = '<share_id>';
```

The link to open is `/@<handle>/r/<share_id>/` for a `recordings` report and `/@<handle>/t/<share_id>/` for a `toots` one.

**What a take-down covers.** The item behind that one share. A link taken down stays down: its row is kept, so the owner can't share that Recording or Toot again (403 `taken_down`), and neither Stop sharing nor deleting it removes it. Taking down a Recording also takes down every Toot that plays it (in its Arrangement or its Sound Pad Performance): those Toots' links answer 404 at once, they drop out of the owner's shares, and sharing one again answers 403 `taken_down`, so no Toot carries the Recording's audio back out. Taking down a Toot covers only that Toot, not the Recordings it plays. To put a link back, set `taken_down_at` to `NULL`; the Toots that play a Recording come back with it. Deleting the account removes it, with the reports.

A profile page, `/@<handle>/`, has Report too (#319, ADR 0021): a `profile_reports` row (the user and when) and a `profile_reported` log line with the Handle. It spends the same reporter and site slots as a link's Report, and a page gets 5 a day. A page lists only live shares, so taking down each of its shares empties it. There's no way yet to take a Handle away.

```sql
-- Newest profile reports first, and what each page lists.
SELECT r.created_at, h.handle, r.user_id FROM profile_reports r
  JOIN handles h ON h.user_id = r.user_id ORDER BY r.created_at DESC LIMIT 20;
SELECT id, kind, item_id FROM shares WHERE user_id = '<user_id>' AND taken_down_at IS NULL;
```

**A Song that's wrong.** Song Creator's end and a locked Song's sheet have Report a problem (#358): a reason (`wrong_notes`, `wrong_sound`, `wrong_title` or `other`, `SONG_REPORT_REASONS` in `src/lib/song-report.ts`) and an optional note of up to 500 characters, from anyone, guests too. Each is a row in D1's `song_reports` (the Song's id, `song_version`, the reason, the note and when; nothing about who sent it) and a `song_reported` log line with the Song, version and reason, never the note. `song_version` is the 16 hex digits in the name of the notes file the reporter heard (`public/catalog/notes/<id>-<version>.json`), so reports from before a fix show as about older notes. Nobody is emailed. The limits are `REPORT_LIMITS` in rows of their own, so Song reports never spend a link's or page's Report slots: a reporter gets 10 an hour, a Song 5 a day and the site 300 an hour (`src/server/song-reports.ts`).

**The owner reads them** in the same Console, worst first:

```sql
-- Songs with the most reports first, with each reason's count and the newest report.
SELECT song_id, COUNT(*) AS reports, SUM(reason = 'wrong_notes') AS wrong_notes,
  SUM(reason = 'wrong_sound') AS wrong_sound, SUM(reason = 'wrong_title') AS wrong_title,
  SUM(reason = 'other') AS other, datetime(MAX(created_at) / 1000, 'unixepoch') AS newest
  FROM song_reports GROUP BY song_id ORDER BY reports DESC, newest DESC LIMIT 50;
-- One Song's reports and notes, newest first.
SELECT datetime(created_at / 1000, 'unixepoch') AS at, song_version, reason, note
  FROM song_reports WHERE song_id = '<id>' ORDER BY created_at DESC;
```

To list them against the catalog, which tells the reports on a Song's notes now from those on older notes, the owner exports the rows from their own terminal and an agent runs `tools/catalog/song_reports.py` on the file:

```sh
mkdir -p tmp && pnpm --dir apps/web exec wrangler d1 execute pedos-production --remote \
  --env production --json --command "SELECT * FROM song_reports" > tmp/song-reports.json
python3 -I tools/catalog/song_reports.py tmp/song-reports.json
```

It takes a CSV of the same columns too. A Song is fixed through `catalog/` like any other (ADR 0003); nothing marks its reports done, and the next export shows them as about older notes.

## Gotchas learned in slice 1

- `apps/web` isn't `"type": "module"`, so Playwright compiles `e2e/` as CommonJS. Use `__dirname`, not `import.meta`.
- Biome treats any function named `use…` as a React hook. That's why the fake-microphone helper is `withFakeMicrophone`.
- Chromium's fake microphone: `--use-file-for-fake-audio-capture=<wav>%noloop` plays the file once. It needs a PCM WAV. Fixtures 090 (G3), 084 (G♯3, two farts) and 065 (Noise-like) are the e2e cases. It plays from the moment the stream opens, before the app captures, so a take loses the file's first tens of ms (60 ms on CI). That cost 094, which is loud from 8 ms, its steady note (#141). A spec whose farts must start whole uses `e2e/fake-microphone.ts`, which plays each fart as Record is pressed, and `waitForOpenMicrophone`, which waits for the app's capture processor rather than getUserMedia (#172).
- Accounts in the journeys (#155): a guest's farts last only the visit (#237, ADR 0013; until 2026-10-28 their Recordings were kept: owner, 2026-10-25, #203), so a spec whose Recordings or Toots outlast a relaunch signs in first (`signInByApi` in `e2e/account.ts`, with the code from `/dev/mail/`). Locally every request comes from 127.0.0.1, one client with 10 codes in 10 minutes, so `ownClient` gives each test its own `cf-connecting-ip`, which Miniflare passes through. It adds the header to Farty's own requests only: on Turnstile's, Chromium blocks the script (`ERR_BLOCKED_BY_ORB`) and the widget never gives a token. `skipWelcome` and `recordAndSave` (`e2e/record.ts`) keep the account step out of the way unless a spec asks for it.
- Through the fake microphone, 4 of 5 Melodic fixtures give a Recording Pitch identical to golden. 094 (low confidence) comes out 20 cents high, still B3. Expect small differences on re-recorded audio. Assert note names, not exact MIDI.
- V8's `2 ** x` and `Math.log2` differ from numpy by an ulp on some pYIN bins. `analysis/numeric.ts` has correctly rounded `exp2` and `log2`. Use them, or bit-identity breaks.
- The timing tests need `fileParallelism: false` (`vitest.config.mts`).
- Safari mutes Web Audio when the silent switch is on unless `navigator.audioSession.type = 'playback'` is set (`context.ts`). The microphone needs `'play-and-record'` while it's open, which is from the first time Record shows to the end of the launch (`keepMicrophoneOpen`), so sounds play in it then too (`setPlaybackSession`). While it's open, WebKit runs iPhone's session in voice-chat mode, which Apple says plays quieter (#369). So a grant the browser remembers (Safari's per-site Microphone setting at Allow) is let go off Record and opens again, without asking, as Record shows (`leaveRecord`). Any other grant stays open, because letting it go would bring back the prompt (#222). Muting the track (`enabled = false`) doesn't help: WebKit counts it as capturing.
- The Welcome icon uses `next/image` with `unoptimized`, because Workers has no image optimizer.
- 16-bit WAV: encode as `round(x × 32768)`, clamped, and decode as `/32768`, as other decoders do.
- A page prerendered by `generateStaticParams` is served on Workers from the static-assets incremental cache (`open-next.config.ts`), which `opennextjs-cloudflare preview` and `deploy` fill. Without it, such a page 404s on Workers though `next build` lists it. `/compose/[song]/` is prerendered with `dynamicParams = false`, so a link or a search engine gets each Song's title, and an unknown Song 404s. The service worker keeps one Song page, `/compose/song/` (`/shell.json`), and answers offline with it for every Song's page; it reads the Song from the address, because Next's router takes its URL from `location` (#322). It never keeps a Song's own page: nothing would refresh it, so after a deploy it would run an older build's code and catalog.
- The Song Catalog is data, not code (#322), split so Compose stays quick with 1,000 Songs (#323). `src/lib/catalog/generate.ts` writes an index, `public/catalog/songs-<hash>.json`, with each Song's title, other names (from `tools/catalog/titles-*.txt`, for search), pitches and note lengths, which is all Compose and Pitch Coverage read; and each Song's notes, `public/catalog/notes/<id>-<hash>.json`, which Song Creator and a Toot's screen fetch as the Song opens (`loadSong`). The service worker keeps the index with the shell, and every Song's notes in a cache of their own (`pedos-notes-v1`, #138): it fetches them, 6 at a time, once it's active and whenever a page fetches an index, never while installing, so a new build's worker takes over without waiting on them (#350). Routes and the server import `song-index.generated.ts`, and tests `songs.generated.ts`, which adds the notes. Biome refuses both in `src/components/` and `src/lib/`, so the Songs never reach the JavaScript bundle. It ships every Song in the catalog but `ode-mutopia`, the same tune as `ode` (#350). Run the generator again after a change to `catalog/`, the titles files or `fixtures/golden/songs/`; `catalog.test.ts` fails while it's out of date.
- Both Web Workers load one Turbopack script, each with its own chunks in the URL's fragment (`#params=`), and a worker runs what its script's response URL says. The service worker keeps a copy with no URL, or a worker started offline runs the other worker's chunks.
- Playwright's `evaluate` counts as a tap, and Chromium gives every page Playwright loads the activation of one. To test a page that was never tapped, override `UserActivation.prototype.hasBeenActive` in an init script, as `song-creator.spec.ts` does.
- On macOS, the journeys run in full Chromium (`channel: 'chromium'` in `playwright.config.ts`), not the chrome-headless-shell CI runs on Linux. macOS takes the shell, a bare executable, for an app of whatever launched it. From the Claude desktop app's shells that's a second Claude, which loginwindow force-quits 32 s after launch. The test then running fails with "Target page, context or browser has been closed" in its call log, often as a timeout on the step it was waiting in (#234). `playwright install chromium` installs both. `e2e/toots.spec.ts` launches its own browser with the same `channel`. Full Chromium also reports Playwright's off-the-record context as `in-incognito` among its installability errors, which `e2e/install.spec.ts` ignores.
- `decodeAudioData` detaches the `ArrayBuffer` it's given. Pass it a copy (`wav.slice(0)`) of audio you still need, as Song Creator does with a Toot it hasn't saved.
- `cloudflare-env.d.ts` types the bindings for `getCloudflareContext()`. Regenerate it with `pnpm cf-typegen` after any change to bindings or vars; `pnpm typecheck` fails while it's out of date. It declares the Workers runtime's globals over the DOM's, so browser code sometimes needs the DOM's own form, such as `window.addEventListener` or `appendChild`.

## Shell gotchas

- zsh has `noclobber` set: overwrite a file with `>|`, and use `bash -c` for `set -- $words` loops.
- To call `gh.sh` through a variable, keep only its path in it: `G=~/.claude/skills/serp-github-app/scripts/gh.sh; bash $G pr view <n>`. zsh doesn't word-split `$G`, so `G="bash <path>"; $G ...` fails: zsh looks for one command named `bash <path>`. Writing the whole `bash ~/.claude/skills/serp-github-app/scripts/gh.sh ...` call, as this page does, works too.
