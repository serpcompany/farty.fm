# Browser gotchas

What the browser taught the web app's `src/lib`: audio, the microphone, storage, tabs and installing. The rest of what building the web app taught is in [Web app gotchas](web-gotchas.md).

- **One AudioContext.** iPhone Safari allows only a few, so `audio/context.ts` makes one and keeps it until the page hides. It starts only in a tap: Record, Play, or `startAudioInTap` for a screen that plays after an await, such as Song Creator. One that lived through a hidden page, or was made while hidden, is closed and replaced once the page shows: on iPhone it can say it runs while its clock stands still, so nothing plays or records. Production's reports since #247 were all that, on the first tap after the app came back, and a fresh context recorded (#280). Closing a context never fires `onended` on what plays on it, and its `state` says `closed` only once the close settles, so the player stops its sound and reports the end itself first (`whenClosing`, `isClosed`). The kept microphone moves to the new context with its stream (`moveMicrophone`), so the first Record tap after coming back records at once, from the back-forward cache too (#283).
- **The microphone's grant on iPhone Safari (#222).** A page's grant lasts 24 hours while capture runs. Once capture stops, and a muted track counts, a `getUserMedia` outside a tap asks again after 1 minute, and any call after 10. So `keepMicrophoneOpen` opens without a tap only within 50 s of capture stopping (`microphone-grant.ts`), or when the browser keeps the grant itself, as Safari's per-site setting at Allow does. `navigator.permissions` also says `granted` while the page's own grant lasts, so only an answer from before the page was granted counts as the browser's.
- **Interruptions.** On iPhone, Siri, an alarm, a call banner or hiding the page mutes the track or stops the context without ending it. The capture processor's pre-roll is flushed, and capture goes on with the same stream once the track unmutes and a tap starts the context. A stream kept through an interruption can come back sending exact zeros (#172, #222), so its first take opens a fresh stream in the same tap. A call or another app ends the track, and the take with it. iPhone Safari mutes a hidden page's stream, so it's kept; a browser that keeps listening while hidden has it released after 1 s, since iPhone may unmute it just before it says the page shows. A computer's product page releases it (#199).
- **The capture processor** is an AudioWorklet loaded from a Blob URL of its source (`capture-processor.ts`), so a busy page can't drop samples. It keeps the last 0.3 s in a ring, which each take starts with, and sends a first batch in the first render quantum after `start`, so the page knows capture began. Its node must reach the destination to be pulled, through a gain of 0 that keeps the microphone off the speaker, and `close` makes `process` return false so the audio thread frees it.
- **A take whose first batch never comes (#248).** On an iPhone, the audio clock can stop, or the stream can stop feeding the graph while its track still looks live. Neither recovers by itself. A take with no first batch within 3 s fails with an error named `NoAudio<State>Clock<Ran|Stopped>`, which its report keeps. The recorder then releases the microphone, stops any sound started meanwhile, and replaces the shared AudioContext (`replaceAudioContext`), so the next tap opens both afresh (`recorder.ts`). A take whose context's clock stood still (`stoodStill`) tries once more by itself, on a fresh stream and context, and reports `mic-start-retried`; one whose stream fed the graph nothing doesn't, and the next tap opens a fresh stream. A take's batches reach Record's level from the first, the pre-roll's included, exactly as the take keeps them (#281).
- **The playhead** (`playbackPosition` in `audio/player.ts`) follows the context's clock, which runs ahead of the speaker by the output's latency (`outputLatency`, 0.15 to 0.25 s on Bluetooth), so that's taken off where the browser reports it. A stop on a suspended context, as on iPhone when the page hides, waits for a clock that stands still, so the player reports the end itself.
- **A Pad plays on the press** (`pointerdown`), so each finger plays its own Pad at once, but a touch browser counts only the release (`click`) as a tap that may start audio, so that's where `startAudioInTap` runs; a `click` with `detail === 0` is the keyboard's Enter or Space, which plays. On iOS, when the context isn't running yet (opening `/compose/pad/` directly, after the page was hidden, or after `replaceAudioContext`), the sound starts on the release. Every tap plays its own buffer, so taps overlap and mix (`audio/pad-player.ts`, #277).
- **The buzz.** `navigator.vibrate` isn't there in Safari on iPhone, nor in jsdom or happy-dom, so Record buzzes only where the browser has it, and `record-states.interaction.test.tsx` stubs it and removes it after each test.
- **Share needs a fresh tap.** Safari opens a share sheet only right after a tap, so a link that arrives after an await (`needsTap`) shows "Your link is ready", whose Share link offers it from its own tap (`src/lib/sharing.ts`).
- **IndexedDB.** The `pedos` database is at version 8: version 1 held Recordings, 2 added Toots, and 3 the outbox, downloads and meta. Upgrading to 3 queues every kept Recording and Toot to upload. Version 4 (#268) changes no store: code from before #268 sends an outbox op it doesn't know, such as `place`, as a delete, and would delete the Recording from the account. Version 4 closes that code's connection (`blocking`), it can't open version 3 again (`VersionError`), and an op the running code doesn't know stays queued, unsent (`outbox-send.ts`). Version 5 adds the Sound Pad's `pads` (#277), this browser's only and never synced. Version 6 (#293, ADR 0019) changes no store: it shuts out code from before Trims, which would send a `place` without the Trim and drop the account's Trims while its cursor moved on. Version 7 adds `favorites` (#313), which outlast a guest's visit and go to the account they sign in with. Version 8 (#314) changes no store: it shuts out code that would queue a `place` without the name, and would play a Recording left out of Songs. Every upgrade from version 3 or later sets the last read's `cursor` back to 0, so the next sync reads the whole library once (`readEverythingAgain`): a tab on the older code skipped what it didn't know and still moved the cursor past it. A library with no cursor never read the account and gets none, so `leftByAnAccount` still tells it apart. An older version open in another tab holds the upgrade until it closes (`onWaitingForOtherTabs`), and a later version opening elsewhere makes this tab close its connection. WebKit can drop the connection while a tab sleeps (#222), as `InvalidStateError` or "Connection to Indexed Database server lost": `withDb` runs the work once more on a fresh connection, and since the first run may have committed unheard, a retried save looks for its own write first (`holds`). A transaction names `outbox` before its first request: asking for a store after a request aborted the transaction throws, and leaves the requests already made, and `tx.done`, unhandled. So a write awaits its requests and `tx.done` together, and one that writes nothing still awaits `tx.done` (`placeRecording`).
- **Tabs.** A sync runs under the Web Lock `pedos-sync`, so a browser's tabs take turns, and tells the other tabs what changed on the `pedos-library` BroadcastChannel. Favorite Songs go to the other tabs on `pedos-favorites`. Each open tab holds `pedos-open`, shared, so a new tab never clears another tab's Toots.
- **Timeouts.** Vitest's fake timers don't drive `AbortSignal.timeout`, so requests time out through `withinTimeout` (`timeout.ts`), a `setTimeout` the tests can run.
- **Stale builds (#222).** A tab opened before a deploy later loads scripts the server no longer has. Next.js 16 loads a navigation from another build in full, and Turbopack retries a failed chunk once; after that, `stale-build.ts` reloads the page once nothing unsaved is on screen (`holdReload`), at most once in 10 minutes a tab, and never with sessionStorage blocked. A failed `import()` is a `TypeError`: "Importing a module script failed." in WebKit, "Failed to fetch dynamically imported module" in Chromium. A worker fires a plain `error` event when its own script fails, and an `ErrorEvent` when an `importScripts` fails: "NetworkError: Load failed" in WebKit, "Failed to execute 'importScripts'" in Chromium.
- **A fieldset lays out its own box (#268).** Chrome lays a `<fieldset>`'s children out in an anonymous box that doesn't take the fieldset's height, so the review's piano keys are laid out by the `div` inside it, and the fieldset only names them (`piano-keys.tsx`).
- **Installing.** iPadOS Safari says it's a Mac and Chrome on an Android tablet says Linux; only touch gives them away (`install.ts`). An in-app browser built on SFSafariViewController sends Safari's exact user agent, so it can't be told apart. The service worker registers only in a build: on `next dev` it would outlive the session on a localhost port other apps share.
