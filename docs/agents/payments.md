# Payments

Paying to save a Toot (ADR 0010): how it works, and the owner's Stripe setup.

- **Payments (#204, ADR 0010).** Saving a Toot costs `TOOT_PRICE` (`src/lib/pricing.ts`), paid through Stripe Checkout, which Stripe hosts. `POST /api/toots/{id}/checkout/` starts a Checkout Session for one Toot (or reuses the open one) and records it, with its Song, in `toot_payments`; when another Toot of the same Song is paid and was never saved (the page closed before the return), it answers `{ paidToot }` and Song Creator saves that one instead of paying twice. `POST /api/stripe/webhook/` checks `Stripe-Signature` with `STRIPE_WEBHOOK_SECRET` and marks the Toot paid on `checkout.session.completed` or `checkout.session.async_payment_succeeded`; `GET /api/toots/{id}/payment/` asks Stripe too, so the return from Checkout doesn't wait on the webhook. `PUT /api/toots/{id}/` answers 402 `payment_required` for a new Toot that isn't paid, and its first save uses the payment up (`saved_at`), so a deleted paid Toot answers 410 even after its tombstone is purged.
- **What counts as paid.** A paid session counts only for the amount and currency its Toot's payment row recorded when the checkout started (`TOOT_PRICE` then), so a payment made before a price change still counts. With Adaptive Pricing, the session still records that price and the buyer's own currency is in `presentment_details`, so it counts too. A Toot whose last session is paid at any other price answers 409 `payment_mismatch` (logged as `stripe_paid_session_refused`) and never starts a second payment. Each user may start 20 checkouts an hour (then 429 `rate_limited`) and have the payment check ask Stripe 60 times in 10 minutes (then it answers from D1, which the webhook keeps).
- **Calling Stripe.** The Worker calls Stripe with `fetch` (`src/server/stripe.ts`), with no SDK, on a pinned API version (`STRIPE_API_VERSION`), with an idempotency key on each new session, a 10-second timeout and each answer checked with zod; a failure keeps only Stripe's status (0 unreachable, 502 malformed), never its answer or the key, and answers 502 `payments_failed`. A webhook's signature may match any of its `v1` values, as Stripe signs with both secrets while one is rolled, and its timestamp must be within 300 seconds.
- **Keys, and where saving is paid.** `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` are Worker secrets the owner sets from their own terminal (below), never in `wrangler.jsonc`. Production takes only live keys (`sk_live_`, `rk_live_`) and live events; Staging and local runs only test keys (`sk_test_`, `rk_test_`) and test events. Without a key of its mode, an environment where saving is paid answers 503 `payments_unavailable`, which Save shows. A local run on a local host with no key uses the dev checkout (`/dev/checkout/`, and `POST /api/dev/checkout/`, which marks a started checkout paid), for the journeys and tap-throughs; both answer 404 anywhere else. Saving is paid everywhere: Production in live mode since #258 (2026-10-28), and so is a Production build run locally (`builtFor()`), on both the browser's and the server's side, through the dev checkout when it has no key. `savingIsPaid` (`src/lib/pricing.ts`) is the one switch: putting `'production'` back in its `FREE_SAVING` makes Production save free again (the `free` kind of `Payments`), say if live payments break. Production's paid save has its own journey, run by hand ([Tapping through](web.md#tapping-through)). The owner's Stripe steps are below.

## Stripe

Saving a Toot is paid on Staging in Stripe's test mode, and on Production in live mode (ADR 0010, #258). The code is done; the account and its keys are the owner's.

**The owner, once, for Staging (test mode):**

1. In the Stripe Dashboard, with **Test mode** on, open **Developers → API keys** and create a restricted key with **Write** on **Checkout Sessions** (everything else None), or use the test secret key.
2. Open **Developers → Webhooks → Add endpoint**: URL `https://staging.farty.fm/api/stripe/webhook/`, events `checkout.session.completed` and `checkout.session.async_payment_succeeded`. Set the endpoint's API version to `2026-08-26.dahlia`, the version every request pins (`STRIPE_API_VERSION`), so the events and the return read a session in the same shape. Keep the trailing slash: the Staging gate lets only that exact path through. Keep the endpoint's signing secret for the next step.
3. Set both on the Staging Worker (`pedos-web-staging`) from your own terminal in `apps/web/`. Each command asks for its value:
   - `pnpm exec wrangler secret put STRIPE_SECRET_KEY --env staging`, with the key from step 1;
   - the same with `STRIPE_WEBHOOK_SECRET`, with the signing secret from step 2.

   An agent then checks both by name with `wrangler secret list --env staging`. Never paste either value into chat.
4. In **Settings → Payments → Payment methods**, leave Cards, Apple Pay and Google Pay on. Hosted Checkout needs no Apple Pay domain setup. Checkout asks for cards only (Apple Pay and Google Pay are cards), since a slower method would leave the Toot unsaved after the return. Adaptive Pricing can stay on: the session still records 99 `usd`, and the buyer's own currency is in `presentment_details`, so a payment in it counts. Whether to offer local currencies is your call.
5. Pay once on https://staging.farty.fm with Stripe's test card `4242 4242 4242 4242`, and check that the Toot shows as saved and the payment shows in the Dashboard.

**For Production (live mode, #258):** the same steps with **Test mode** off: a live restricted key, and a live webhook endpoint on `https://farty.fm/api/stripe/webhook/`, set on `pedos-web-production` with `--env production`. Done on 2026-10-28: the owner set both secrets, and an agent checked them by name with `wrangler secret list --env production`. The code takes only live keys and live events there (#213), and charges there since #258. Left for the owner, once a promotion has taken #258 to farty.fm: pay $0.99 once on https://farty.fm with a real card, refund it in the Dashboard, and check that the Dashboard shows the live payment and the webhook's delivery. Google Play's billing policy (#114) is settled before the Play app ships.
