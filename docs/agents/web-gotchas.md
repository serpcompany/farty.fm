# Web app gotchas

What the web app taught its builders, kept so the next change doesn't relearn it. What the browser taught `src/lib` (audio, the microphone, IndexedDB, tabs and installing) is in [Browser gotchas](browser-gotchas.md).

## Learned in slice 1

- `apps/web` isn't `"type": "module"`, so Playwright compiles `e2e/` as CommonJS. Use `__dirname`, not `import.meta`.
- Biome treats any function named `use…` as a React hook. That's why the fake-microphone helper is `withFartingMicrophone`.
- Accounts in the journeys (#155): a guest's farts last only the visit (#237, ADR 0013; until 2026-10-28 their Recordings were kept: owner, 2026-10-25, #203), so a spec whose Recordings or Toots outlast a relaunch signs in first (`signInByApi` in `e2e/account.ts`, with the code from `/dev/mail/`). Locally every request comes from 127.0.0.1, one client with 10 codes in 10 minutes, so `ownClient` gives each test its own `cf-connecting-ip`, which Miniflare passes through. It adds the header to Farty's own requests only: on Turnstile's, Chromium blocks the script (`ERR_BLOCKED_BY_ORB`) and the widget never gives a token. `skipWelcome` and `recordAndSave` (`e2e/record.ts`) keep the account step out of the way unless a spec asks for it.
- Re-recorded through Chromium's fake audio device in slice 1, 4 of 5 Melodic fixtures gave a Recording Pitch identical to golden. 094 (low confidence) came out 20 cents high, still B3. Expect small differences on re-recorded audio. Assert note names, not exact MIDI.
- V8's `2 ** x` and `Math.log2` differ from numpy by an ulp on some pYIN bins. `analysis/numeric.ts` has correctly rounded `exp2` and `log2`. Use them, or bit-identity breaks.
- `next dev` adds a trailing slash to every path (`trailingSlash: true`), and Better Auth's routes have none, so `auth-request.ts` forwards each sign-in request without it.
- Safari mutes Web Audio when the silent switch is on unless `navigator.audioSession.type = 'playback'` is set (`context.ts`). The microphone needs `'play-and-record'` while it's open, which is from the first time Record shows to the end of the launch (`keepMicrophoneOpen`), so sounds play in it then too (`setPlaybackSession`).
- Farty's icons use `next/image` with `unoptimized`, because Workers has no image optimizer.
- 16-bit WAV: encode as `round(x × 32768)`, clamped, and decode as `/32768`, as other decoders do.
- A page prerendered by `generateStaticParams` is served on Workers from the static-assets incremental cache (`open-next.config.ts`), which `opennextjs-cloudflare preview` and `deploy` fill. Without it, such a page 404s on Workers though `next build` lists it. `/compose/[song]/` is prerendered with `dynamicParams = false`, so a link or a search engine gets each Song's title, and an unknown Song 404s. The service worker keeps one Song page, `/compose/song/` (`/shell.json`), and answers offline with it for every Song's page; it reads the Song from the address, because Next's router takes its URL from `location` (#322). It never keeps a Song's own page: nothing would refresh it, so after a deploy it would run an older build's code and catalog beside the current build's database. `/compose/song/` and `/compose/pad/` are static segments, so Next serves them before `[song]`, and the catalog generator refuses `song` and `pad` as Song ids.
- The Song Catalog is data, not code (#322), split so Compose stays quick with 1,000 Songs (#323). `src/lib/catalog/generate.ts` writes an index, `public/catalog/songs-<hash>.json`, with each Song's title, other names (from `tools/catalog/titles-*.txt`, for search), pitches and note lengths, which is all Compose and Pitch Coverage read; and each Song's notes, `public/catalog/notes/<id>-<hash>.json`, which Song Creator and a Toot's screen fetch as the Song opens (`loadSong`). Both are named by their content, so they never change under one name. Routes and the server import `song-index.generated.ts`, and tests `src/test-support/songs.generated.ts`, which adds the notes. Biome refuses both in `src/components/` and `src/lib/`, so the Songs never reach the JavaScript bundle. It ships every Song in the catalog, the iPhone app's 12 first, but `ode-mutopia`: the same tune as `ode`, kept in the catalog to exercise the reference engine's importer (#350). Each Song's notes come from its golden copy, and the generator refuses a copy imported with other render arguments than its catalog entry's, in another meter, or with a note past the excerpt's end, so one left over from an older entry or edited by hand fails (#350). Run `tools/melody-lab/export_golden.py`, then the generator, after a change to `catalog/`, and the generator after one to the titles files or `fixtures/golden/songs/`; `catalog.test.ts` fails while it's out of date.
- The service worker's notes cache holds two catalogs' notes, at least 2000 files and twice the Songs of the latest index it read, however large the catalog grows, and trimming never deletes that index's own. Installing keeps only the shell and the index; the notes come once the worker is active, without holding the activation, which would keep each page's requests waiting on a thousand Songs' notes, so a new deploy's worker takes over at once (#350). An index install couldn't fetch, or notes the browser stopped the worker part way through, come on the next fetch of the index.
- Both Web Workers load one Turbopack script, each with its own chunks in the URL's fragment (`#params=`), and a worker runs what its script's response URL says. The service worker keeps a copy with no URL, or a worker started offline runs the other worker's chunks.
- A Song's page names the tab with the Song's title once the Song Catalog loads (`SongCreatorFromAddress`). The page's own metadata title ("Compose · Farty") can land after that, as it does when hydration is late on a busy phone, so the page sets the Song's title again whenever `<title>` changes. Leaving the Song by a tab, the next page's title lands before the effect's cleanup runs, so it writes the title only while the address is still the Song's (#351). `song-creator.spec.ts` slows the CPU six times to make hydration late.
- Playwright's `evaluate` counts as a tap, and Chromium gives every page Playwright loads the activation of one. To test a page that was never tapped, override `UserActivation.prototype.hasBeenActive` in an init script, as `song-creator.spec.ts` does.
- `decodeAudioData` detaches the `ArrayBuffer` it's given. Pass it a copy (`wav.slice(0)`) of audio you still need, as Song Creator does with a Toot it hasn't saved.
- `cloudflare-env.d.ts` types the bindings for `getCloudflareContext()`. Regenerate it with `pnpm cf-typegen` after any change to bindings or vars; `pnpm typecheck` fails while it's out of date. It declares the Workers runtime's globals over the DOM's, so browser code sometimes needs the DOM's own form, such as `window.addEventListener` or `appendChild`.

## The screens and routes

- A control's visible text is read as one string, its parts joined with no space, so a Sound Pad's Pad and each row of its chooser keep a space between their visible parts and name themselves in the order they show them (`pad.tsx`, `pad-chooser.tsx`). Without it, axe reads "G3Recording 1" and fails WCAG 2.5.3, label in name.
- The root layout's inline script sets `data-welcomed` on `<html>` from `localStorage` before paint, so a touch tablet shows a returning visitor the app and a new one the lander (the `unwelcomed` variant in `globals.css`) with no flash. A computer (the `desktop` variant: 768px and wider, with a mouse or trackpad) gets the lander on every tab by CSS alone.
- The manifest is a route handler, not `manifest.ts`, so the layout can link it with `crossorigin="use-credentials"`. Chrome fetches a manifest without credentials, which behind the Staging password gets a 401, and Next adds the attribute itself only on Vercel previews.
- The home page writes its own canonical, the bare origin, because Next adds a trailing slash to the layout's. The 404 page has none, since the layout's would name the missing URL.
- The shell picks the current tab from `useSelectedLayoutSegments()`, not `usePathname()`. The 404 page is prerendered once, as `/_not-found`, and served at every missing address, so the server draws it with no tab while `usePathname()` in the browser reads the address. Under a tab (`/compose/not-a-song/`) that drew Compose as current and broke hydration (React error #418). The segments come from the route tree sent with the page, which says `/_not-found` on both sides.
- Every Toot opens on one static page, `/toots/toot/?id=`, because a Toot's id is made on the device. The service worker keeps it, matched without its query, with the one Song page and the Sound Pad, from `/shell.json`.
- Compose's rows have `content-visibility: auto` with an intrinsic size of about a row (49 px unlocked, 107 px locked), so a row off the screen skips its layout and paint and keeps the room it last took: with 1,000 Songs, laying out every row was most of the time Compose took to open, search and scroll (#323). Rows are memoized, and a locked row works out its Arrangement, for its Needs line, only while it's within a screen of the viewport (`useNearViewport`, one IntersectionObserver for every row).
- Song Creator plays the Toot once it's made, and only a tap starts audio: the taps that open it call `startAudioInTap`, and one opened from a link or a reload waits for a tap (`navigator.userActivation`).
- Back from Song Creator or a Toot's screen goes back in history when Compose or Toots opened it, and otherwise replaces the page, so the system Back never opens it again (`back-link.tsx`).
- Done or Try it on a Result keeps the record flow open until the next page shows. Closed first, it would show the Record screen idle on the way, which opens the microphone.
- The note view takes a tap anywhere and plays the nearest note. Each note is also a button, out of the pointer's way, for the keyboard and screen readers.
- Back from Checkout, Song Creator makes the same Toot again, with the id it was paid for (ADR 0010), and waits for a tap to play it.
- The lander's screenshots are a `<picture>` whose source applies from 768px and whose `<img>` is a transparent pixel, loaded lazily, so a phone, or a lander hidden once Farty is open, downloads none of them. Download App's QR code is drawn on the server at build (`download-qr.tsx`), so no QR library reaches the browser, black on white in both themes, as scanners expect.
- The install prompt shows once, after the first saved Recording, and waits for the record flow to close. It also registers the service worker and, signed in with a Recording, asks the browser to keep Farty's storage. A guest's farts last only the visit, so a guest's browser isn't asked (#237).
- The account step comes back after a reload while it was open (a phone dropping the tab during Mail), and asks a browser whose session ended to sign in again, once a visit.
- Leaving the Toots tab lets go of the audio its rows decoded. A Toot that plays keeps playing into its screen, as on the iPhone; another tab stops it.
- Profile's Safari tip (Page Menu, Website Settings, Microphone: Allow) follows Apple's "Browse the web privately in Safari on iPhone" (iOS 27).
- `--brand` is the app icon's pink, for accents. `--brand-strong`, a deeper shade, goes behind white text, where it keeps a 5:1 contrast. `--record-screen`, the Recording screen's red behind white text, keeps 4.7:1.
- `error.tsx` and `global-error.tsx` report what broke a screen as `uncaught-error` and offer a reload. Next passes only what its built-in boundary catches to `window.reportError`, which `installErrorReporting` hears; an error these catch, Next only logs, so they report it themselves. `global-error.tsx` replaces the root layout, so it brings its own `<html>`, styles and viewport.

## The journeys

- Every spec imports `test` and `expect` from `e2e/test.ts`, which fails a test on any console error or page error. A test that causes one on purpose (an aborted route, offline, a 404, the synthetic crash) names it with `pageErrors.expect(...)`. A second browser comes from the `newContext` fixture, and a persistent profile is watched with `pageErrors.watch(context)`. A context's init script also runs in each new page's `about:blank`, whose opaque origin has no `localStorage`, `navigator.storage` or `navigator.mediaDevices`, so the init scripts that use them skip a document without an origin.
- No test waits a fixed time, and none is retried (`retries: 0`). A check that something doesn't happen waits for the step that would have done it: the page running its pending work, the effect that would act included (`pageSettled`, a background-priority task: `requestIdleCallback` starves on a busy machine), the page clock run past the app's timer (`record-grant.spec.ts`), what the app does instead (the capture processor loading, Save disabled while the visit opens), or an event (a worker's `error`, with the Navigation API's `navigate` events to catch a reload). The fake microphone holds a press until its own audio clock has played the fart for 150 ms, and a take until the app has captured 1.3 s past the fart.
- A failed journey keeps its trace (screenshots and DOM snapshots at each step) and a screenshot, not a video. Recording video for every test, to keep only the failures', slowed teardown past the 30 s test timeout on a loaded machine. A journey that must fit inside one of the app's own timeouts, such as the 5 s session read, gives the fake microphone `answersAfterMs: 0` instead of the 800 ms the "Getting the mic ready" journeys need.
- axe can't tell the background of text over a gradient drawn by a sibling layer, as on the product page's hero. It marks that text as needing review (`bgOverlap`), not as a violation, so `e2e/accessibility.ts` measures it: it screenshots the text, then the same box with every text colour transparent, and checks the contrast only at the pixels the text changed. It reads every text colour and takes every first screenshot before hiding any text, because a button's colour transition leaves its computed colour transparent for a moment after the hiding style is removed.
- Journeys record through a fake microphone in the page (`e2e/fake-microphone.ts`), never Chromium's file device. That device (`--use-file-for-fake-audio-capture`) plays the file from when the microphone opens, not from the tap, so on a busy machine a take that started late missed the whole fart. `withFartingMicrophone` (`e2e/record.ts`) sets `e2e/test.ts`'s `fakeMicrophone` option, which adds the microphone to the test's context and to each `newContext`, and grants it, so Record opens it as it shows. A journey about the first tap or the grant passes `granted: false` (#149). The microphone plays a fixture (090 is G3, 084 two farts, 065 Noise-like) as Record is pressed (`fartAndRecord`), after `waitForOpenMicrophone` has seen the app's capture processor, `farty-capture`, not just getUserMedia (#172). It plays each fart through a gain (`gainDb`, as `fartGain`) and notes the fart's peak as played (`fartPeak`): 090 peaks at -1.2 dBFS, so 49 dB down the microphone hears it peak at about -50 dBFS, a quiet take (`record-quiet.spec.ts`), and 0.3 dB up it peaks above the level a take is turned up to, so it's saved at its own level (`record-warm.spec.ts`, #279).
- `record-states.spec.ts` holds the capture node's batches back from the app to see the grey screen. The hold must stay well under `firstBatchTimeoutMs` (3 s, imported from `src/lib/audio/recorder.ts`), after which the take gives up as "couldn't start": more than 5 batches is about 430 ms, so a runner too slow for that margin fails the check rather than flaking later. `record-grant.spec.ts`'s `stallContextsOnHide` breaks each context with a capture processor as the page hides, as iPhone Safari did (#280).
- `touchDrag` (`record-noise.spec.ts`) sends a finger's press, drag and lift as touch events through the DevTools protocol (`Input.dispatchTouchEvent`), which Chromium turns into pointer events with `pointerType` touch, as on a phone; `page.mouse` sends a mouse's. A review is a modal, so the tabs under it are inert and hidden from screen readers, and a journey finds them by tag.
- A Song opened by a tap plays by itself once its Toot is made, Try again included (#234). Song Creator shows Ready or Playing in the same render that makes the Toot, so a page that shows Ready never started a play.
- A relaunched or second profile's service worker answers navigations without the Staging gate's credentials, so the Toots, sync, Song Creator, sharing, friends and Get Farty journeys block service workers, except in their offline tests. With none to answer for it, a catalog the server won't give shows "Couldn't load the Songs.", which `compose.spec.ts` checks that way.
- Chromium can't emulate `display-mode`, so `profile.spec.ts` answers `matchMedia` itself, and fires `beforeinstallprompt` only for an installable site it trusts, so `e2e/install-prompt.ts` fires it as Farty listens. WebKit drops a `navigator.mediaDevices` wrapper nothing holds, so the fake microphone holds it. `next dev` puts its Dev Tools button over the Recordings tab at phone size, so `tabs.spec.ts` hides it.
- The fixtures behind the counts: loading the whole Fixture Library (38 fixtures) unlocks every Song the app's Pitch Coverage unlocks on the reference's analysis of each fixture (`songsTheFixtureLibraryUnlocks` in `e2e/songs.ts`, from `fixtures/golden/recordings/` through `test-support/golden-analysis.ts`), since Songs play every burst of a fart (ADR 0016). So every journey's count follows the catalog instead of a number typed in, and `fixture-library.test.ts` checks that the app's own analysis of the fixtures unlocks the same Songs. In the Library, 002 is Recording 1: a 4.039 s fart in a 4.2 s take, and a row shows its fart's length rounded down, which Needs is measured against (#227). Without 002, Amazing Grace's 2.98 s note on E3 outlasts every fixture near it, one of 40 Songs that lock (`song-listing.test.ts`). Four takes, 095 (F2), 017 (D♯2), 022 (E2) and 002 (A♯2), unlock Mary Had a Little Lamb and more Songs (`songsUnlockedAt` in `e2e/songs.ts`); the third, 022, unlocks Hot Cross Buns, so its Result offers Done, not Record another. Mary needs 002, the only one of the four whose fart outlasts its 1.40 s last note (ADR 0011). A re-recorded take keeps its Recording Pitch, but its settle time depends on where the fart falls in the take (095: 6 to 29 ms, against golden's 29), and so do the notes a Song needs after that one fart, so `compose.spec.ts` checks their shape there, not golden's notes, and `pitch-coverage.test.ts` pins them on the golden 095.
- With 1,000 Songs (#323), a Compose row works out its missing notes only near the screen, so a journey scrolls a row into view before reading its Needs. A Song's title can start another's, and every Song has a heart named "Favorite <title>", so journeys find a Song by its `data-song` or an exact name, and a Toot's row by its exact title.
- `record-melodic.spec.ts`'s Re-scan journey stores 090's analysis as an older Recording Analysis (version 4) left it, with no note, and until Re-scan is tapped makes every read of its audio miss, as for an account Recording not downloaded yet, so the open's upgrade can't run first.
- `song-creator.spec.ts` makes a Toot of the 12 Songs the iPhone app shipped and Hot Cross Buns, the first of the catalog Songs Compose lists since #229: a Toot of every Song would take it past its time limit, and the unit tests check every Song against the golden data.
- With `E2E_EVIDENCE_DIR` set, the Song Creator, Sound Pad and shared Toot journeys write their evidence there for the PR, such as screenshots with animations off, the Sound Pad take's Toot WAV and presses, and the shared Toot's link image.
- On macOS, the journeys run in full Chromium (`channel: 'chromium'` in `playwright.config.ts`), not the chrome-headless-shell CI runs on Linux. macOS takes the shell, a bare executable, for an app of whatever launched it. From the Claude desktop app's shells that's a second Claude, which loginwindow force-quits 32 s after launch. The test then running fails with "Target page, context or browser has been closed" in its call log, often as a timeout on the step it was waiting in (#234). `playwright install chromium` installs both. `e2e/toots-kept.spec.ts` launches its own browser with the same `channel`. Full Chromium also reports Playwright's off-the-record context as `in-incognito` among its installability errors, which `e2e/install.spec.ts` ignores.

## Unit and interaction tests

- Tests that mount the real providers render `FartyProvider` and mock `next/navigation`'s `usePathname` (the Song Catalog reads it) and `@/lib/catalog/load-songs`, and `./account-provider` only where a screen reads `useAccount()`. happy-dom fetches the Song Catalog's `preload` from a server that isn't there, so they mock `react-dom`'s `preload` too (`test-support/app-providers.ts`). The mocked catalog is the index (`test-support/fake-load-songs.ts`): importing `songs.generated.ts`, a thousand Songs' notes files, takes longer than the first test's time (#350).
- happy-dom lays nothing out, so every row starts on the screen in `use-near-viewport.interaction.test.tsx`.
- Next's `Link` drops the trailing slash in a test, outside a build with `trailingSlash`, so hrefs read `/u/alice/t/…` with no slash.

## Shell gotchas

- Where zsh has `noclobber` set, as on the macOS machine, overwrite a file with `>|`, and use `bash -c` for `set -- $words` loops.
- To call `gh.sh` through a variable, keep only its path in it: `G=~/.claude/skills/serp-github-app/scripts/gh.sh; bash $G pr view <n>`. zsh doesn't word-split `$G`, so `G="bash <path>"; $G ...` fails: zsh looks for one command named `bash <path>`. Writing the whole `bash ~/.claude/skills/serp-github-app/scripts/gh.sh ...` call, as this page does, works too.
